title: PostgreSQL compilation
description: The SQL that YoDb sends to a database, and why it is safe.

> **This page describes how YoDb works inside.** You do not need it to write a
> catalog or a query. The classes it names are internal and may change; see
> [Compatibility](/reference/compatibility).

Every read of a PostgreSQL source is one SQL statement that YoDb writes. This
page shows what that statement looks like. A query over several sources becomes
several such statements, one per source.

Writing the statement is separate from running it. The compiler produces the
SQL text and, apart from it, the list of values. Another component then takes a
connection from the pool and runs it.

## Example

Given this logical query:

```yaml
from: {dataset: customer}
select: [id, name, status]
where: {field: status, op: eq, value: active}
order_by:
  - {field: name, direction: asc}
page: {first: 25}
```

and a reviewed catalog mapping:

```text
customer.id     → public.accounts.account_uuid
customer.name   → public.accounts.company_name
customer.status → public.accounts.account_status
```

YoDb produces the following compiled form:

```sql
SELECT "account_uuid" AS "id", "company_name" AS "name", "account_status" AS "status"
FROM "public"."accounts"
WHERE "account_status" = %s
ORDER BY "company_name" ASC, "account_uuid" ASC
LIMIT %s
```

```text
parameters: ("active", 25)
output columns: id, name, status
```

The caller never submits `public.accounts`, `account_status`, SQL, or `%s`.
Those identifiers are derived only from the active catalog's approved source
binding. The caller's `active` value is a separate parameter, never
interpolated into SQL text.

## What is turned into SQL

For one source, the compiler writes:

- selected fields;
- Boolean `all`, `any`, and `not` expressions;
- `eq`, `ne`, `in`, `not_in`, `is_null`, `is_not_null`;
- numeric and timestamp range operators: `gt`, `gte`, `lt`, `lte`;
- deterministic ordering, including the logical-ID tie-breaker;
- bounded `LIMIT` from the page size and `maximum_results` constraint.

The compiler quotes every resource, column, and output alias derived from the
catalog. It also rejects an invalid qualified resource instead of attempting
to construct SQL from it.

## What is not turned into SQL

- **Work across sources.** Matching rows from two sources, and joins between
  datasets, happen in YoDb after the reads. There is never a SQL join across
  databases.
- **`contains` and `starts_with`.** YoDb applies these itself after reading,
  because databases disagree on how text compares. See
  [Limits](/reference/limits).
- **The semantic filter's verdicts.** The model you supply judges rows after
  they are read.

The compiler refuses anything it cannot write correctly. It never drops part of
a query silently. See [Query execution](/query/execution) for how statements are
run.
