---
title: Query execution
description: Run supported structured queries through YoDb's central execution engine.
---

The central execution engine is the supported route from a caller's structured
logical query to normalized logical rows. It owns the orchestration but never
contains SQL, Cypher, credentials, connection-pool logic, or database-driver
objects.

```text
structured query
  → parse and validate against the active catalog
  → resolve approved physical source bindings
  → build one physical plan from source planning adapters
  → compile each remote scan into a native parameterized command
  → execute remote scans through their source execution adapters
  → assemble and complete remaining logical work at the coordinator
  → normalized logical rows
```

## Creating the PostgreSQL path

An application wires each concern once at process startup. The catalog runtime
must already have activated a validated catalog.

```python
from yodb.compilation import PostgresQueryCompiler, QueryCompilerRegistry
from yodb.execution import (
    PostgresQueryExecutionAdapter,
    QueryExecutionAdapterRegistry,
    QueryExecutionEngine,
)

compilers = QueryCompilerRegistry([
    PostgresQueryCompiler(),
])

executors = QueryExecutionAdapterRegistry([
    PostgresQueryExecutionAdapter(postgres_connection_adapter),
])

engine = QueryExecutionEngine(runtime, compilers, executors)
```

`postgres_connection_adapter` is the existing `PostgresConnectionAdapter`. It
resolves the opaque connection reference and leases a bounded pooled connection.
It is not constructed from a caller query.

## Running a query

```python
result = engine.execute({
    "from": {"dataset": "customer"},
    "select": ["id", "name", "status"],
    "where": {"field": "status", "op": "eq", "value": "active"},
    "page": {"first": 25},
})

for row in result.rows:
    print(row["id"], row["name"])
```

The result contains immutable mappings using logical field names only, along
with fingerprints for the normalized query and the activated catalog snapshot.
The central engine does not expose native cursors or native query text.

## Adapter boundaries

Four registry-selected adapter categories isolate providers:

| Adapter | Owns |
| --- | --- |
| connection adapter | credentials, connection settings, and pooling |
| planning adapter | what a source can preserve for one physical fragment |
| compiler adapter | native query construction and parameter binding |
| execution adapter | running native work and normalizing native result rows |

PostgreSQL is the first implementation of both compiler and execution
adapters. A future Neo4j, MongoDB, or other backend provides equivalent
adapters under the same interfaces; the structured caller query and central
engine do not become database-specific.

## V0.1 execution boundary

V0.1 executes both single-source PostgreSQL queries and a bounded baseline
multi-source shape for one logical dataset. The engine has one source-local
`RemoteScan` per participating representation. It assembles contributor rows
onto the identity-source records by the declared logical `id`, then evaluates
the complete filter, global order, and page locally before exposing the
requested projection.

For multi-source queries, only individual top-level `all`/AND predicates owned
by one source may be pushed. Cross-source `any`/OR and `not` expressions stay
at the coordinator. A contributor scan that has a pushed conjunct is also a
required matching-ID set, preventing a non-returned contributor record from
being mistaken for a null field value.

`contains` and `starts_with` currently run only at the coordinator. When a
residual predicate exists, the planner does not push ordering or paging ahead
of it; it uses a bounded remote scan instead. This is slower than native text
pushdown but preserves logical results.

Relationship traversal, semantic search, cursor pagination, key transfer,
parallel scan scheduling, and non-PostgreSQL adapters remain future plan nodes.

## Bounds and explain

The baseline has two hard safety boundaries:

- a remote scan without a result-affecting remote page is capped at 10,000
  rows plus one sentinel row; receiving the sentinel raises
  `query_row_limit_exceeded`;
- coordinator sort/page processing is capped at 50,000 rows; exceeding it
  raises `query_coordinator_limit_exceeded`.

`engine.explain(query)` performs parsing, binding, resolution, and planning
only. It returns a structural plan explanation with source aliases, logical
fields, pushed filter field names, order, and limit—never values, credentials,
physical names, or SQL.
