title: Query model

A query is a JSON object. It asks for records of one dataset: which fields,
which filter, in what order, and how many. Every name in it is a dataset or
field name from your catalog. A query never names a database, a table or a
column, and it is never SQL.

The examples use the sample shop from the
[Quickstart](/getting-started/quickstart).

## A first query

"The names and plans of UK customers, sorted by name, at most 25."

```json
{
  "from": {"dataset": "customer"},
  "select": ["name", "plan"],
  "where": {"field": "country", "op": "eq", "value": "UK"},
  "order_by": [{"field": "name", "direction": "asc"}],
  "page": {"first": 25}
}
```

Run it with `yodb query catalog/ '<json>'`, or with `db.query(...)` from
[Python](/reference/python).

## The keys of a query

| Key | Required | Meaning |
| --- | --- | --- |
| `from` | Yes | The dataset to query: `{"dataset": "customer"}` |
| `select` | No | The fields to return. Default: every public field |
| `where` | No | A filter. Default: no filter |
| `order_by` | No | The sort order. Default: by `id` |
| `page` | No | How many rows: `{"first": 25}`. Default 100, at most 500 |
| `traverse` | No | Follow a relationship to another dataset. See [Joins](/query/joins) |
| `constraints` | No | Extra bounds on the query. See "Constraints" below |

Any other key is refused with `query_shape_invalid`. YoDb never ignores a key
it does not know.

## `select`: which fields

```json
"select": ["name", "country", "plan"]
```

- The `id` field is always returned, even if you do not list it.
- Leave `select` out to get every public field.
- A field that does not exist is refused (`field_not_found`). A field marked
  `visibility: internal` in the catalog is refused too (`field_not_accessible`).
  Neither returns an empty column.

## `where`: the filter

A filter is either one condition, or several combined with `all`, `any` and
`not`.

### One condition

A condition has a `field`, an operator `op`, and usually a `value`:

```json
"where": {"field": "priority", "op": "gte", "value": 3}
```

### Operators

| Operator | Meaning | Works on | Value |
| --- | --- | --- | --- |
| `eq`, `ne` | equal, not equal | every type except `json` and `bytes` | one value |
| `in`, `not_in` | is, or is not, one of a list | the same | a list of up to 1,000 values |
| `gt`, `gte`, `lt`, `lte` | greater or less than | `int`, `float`, `timestamp` | one value |
| `contains` | the text contains this | `string`, `text` | text |
| `starts_with` | the text starts with this | `string`, `text` | text |
| `is_null`, `is_not_null` | has no value, has a value | every type | none |

```json
{"field": "status", "op": "in", "value": ["open", "pending"]}
{"field": "name", "op": "starts_with", "value": "Ada"}
{"field": "plan", "op": "is_null"}
```

Things to know:

- **`contains` and `starts_with` are case-sensitive.** `"ace"` matches
  "Ada Lovelace" and `"ACE"` does not.
- **A record with no value never matches `eq`, `ne`, `in` or a comparison.**
  To find records with no value, use `is_null`. Writing `"value": null` is
  refused.
- **Text cannot be compared with `gt` or `lt`.** Those work on numbers and
  timestamps.
- `contains` and `starts_with` are applied by YoDb after reading the rows, not
  by the database, so pair them with another filter on a large table. See
  [Limits](/reference/limits).

### Value types

The value must have the type of the field.

| Field type | Write the value as | Example |
| --- | --- | --- |
| `string`, `text`, `id`, `uuid` | JSON text | `"UK"` |
| `int` | a whole number | `3` (not `"3"`) |
| `float` | a number | `9.5` |
| `bool` | `true` or `false` | `true` (not `"true"`) |
| `timestamp` | text with a date, a time and a zone | `"2026-01-01T00:00:00Z"` |

A value of the wrong type is refused with `query_value_type_invalid`. A
timestamp without a zone, such as `"2026-01-01"`, is refused as well.

### Combining conditions

`all` means every condition must hold (AND):

```json
"where": {"all": [
  {"field": "status", "op": "eq", "value": "open"},
  {"field": "priority", "op": "gte", "value": 3}
]}
```

`any` means at least one must hold (OR):

```json
"where": {"any": [
  {"field": "priority", "op": "eq", "value": 5},
  {"field": "status", "op": "eq", "value": "pending"}
]}
```

`not` reverses one condition or group:

```json
"where": {"not": {"field": "status", "op": "eq", "value": "closed"}}
```

They nest, up to 32 levels deep and 1,000 conditions in total:

```json
"where": {"all": [
  {"field": "country", "op": "eq", "value": "US"},
  {"any": [
    {"field": "plan", "op": "eq", "value": "pro"},
    {"field": "plan", "op": "eq", "value": "team"}
  ]}
]}
```

A condition compares a field with a value. It cannot compare two fields with
each other.

### A condition written as a sentence

If a semantic filter is configured, a condition can be a sentence that a model
judges:

```json
{"semantic": {"field": "body", "proposition": "the customer is asking about a late delivery"}}
```

It goes where a condition goes: as the whole `where`, or inside `all`. See
[Semantic filter](/query/semantic-filter).

## `order_by`: the sort order

```json
"order_by": [
  {"field": "signed_up", "direction": "desc"},
  {"field": "name", "direction": "asc"}
]
```

`direction` is `asc` or `desc`. Rows are sorted by the first term, and ties are
broken by the next.

YoDb always adds `id` as the last tie-breaker, so the order is the same every
time you run the query. With no `order_by`, rows are ordered by `id`.

`json` and `bytes` fields cannot be sorted on.

## `page`: how many rows

```json
"page": {"first": 25}
```

`first` is the number of rows to return. The default is 100 and the maximum is
500. There is no "next page": to see different rows, narrow the filter or
change the order. `page` takes no other key.

## `traverse`: follow a relationship

`traverse` joins the dataset to another one over a relationship declared in the
catalog:

```json
"traverse": [{
  "relationship": "customer_has_ticket",
  "as": "ticket",
  "select": ["subject", "priority"],
  "where": {"field": "status", "op": "eq", "value": "open"}
}]
```

You get one row per matching pair, with the second dataset's fields prefixed by
the `as` name (`ticket.subject`). [Joins](/query/joins) covers it in full.

## Constraints

`constraints` sets extra bounds for this one query:

```json
"constraints": {"maximum_results": 50, "maximum_latency_ms": 2000}
```

| Key | Meaning |
| --- | --- |
| `maximum_results` | Never return more than this many rows, whatever `page.first` says. At most 500 |
| `maximum_latency_ms` | A time budget for the semantic filter, in milliseconds |
| `maximum_cost` | A cost budget for the semantic filter |
| `minimum_quality` | How confident the semantic filter's model must be, from 0 to 1 |

The last three only stop a query that has a
[semantic condition](/query/semantic-filter). On other queries they are hints to
the planner and never end the query. To limit the time of any query, pass
`--timeout` on the command line or `timeout_seconds` in Python.

YoDb never returns part of an answer. If one database fails, the query fails.

## What a query cannot name

- a database, source, table or column;
- SQL in any form;
- a field that is not in the catalog, or one marked `visibility: internal`;
- an index, an embedding model, or a hint about how to run the query.

This is deliberate. It means a query keeps working when you move data between
databases, and it means a caller cannot reach anything you did not put in the
catalog.

## When a query is refused

YoDb checks the whole query against the catalog before it contacts any
database. A refused query gets an error with a code and the place in the query:

```text
error [field_not_found] at select[0]: Unknown field 'nam' on dataset 'customer'.
```

| Problem | Code |
| --- | --- |
| Not valid JSON, or a key YoDb does not know | `query_shape_invalid` |
| No such dataset | `dataset_not_found` |
| No such field | `field_not_found` |
| The field is internal | `field_not_accessible` |
| A value of the wrong type | `query_value_type_invalid` |
| An operator the field's type does not support | `query_operator_not_supported` |
| A page or list over its limit | `query_limit_invalid` |
| No such relationship | `relationship_not_found` |

The place reads like a path into the query: `where.all[1].value` is the `value`
of the second condition inside `all`. See [Errors](/reference/errors) for every
code.

## What a query cannot do yet

- Count, sum or group. There is no aggregation.
- Fetch a next page.
- Follow more than one relationship.
- Compare two fields with each other.

[Limits](/reference/limits) has the full list.
