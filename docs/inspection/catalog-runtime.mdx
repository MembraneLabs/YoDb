> **This page describes how YoDb works inside.** You do not need it to write a
> catalog or a query. The classes it names are internal and may change; see
> [Compatibility](/reference/compatibility).

The catalog runtime is the part that decides which catalog queries run against.
Its rule is all or nothing: a catalog is put into use only when every source in
it validates. If a new version fails, the previous one stays in use.
`yodb.connect` creates the runtime, and `db.refresh()` asks it to try again.

`InMemoryCatalogRuntime` holds three things together in memory: the loaded
`Catalog`, what inspection found in each source, and each source's validation
report.

```text
datasets.yaml + sources.yaml + relations.yaml
                    |
                    v
              load_catalog()
                    |
                    v
       SourceInspectionRegistry (by source kind)
                    |
        inspect source → validate source bindings
                    |
                    v
   candidate CatalogEvaluation (all configured sources)
                    |
           all sources valid? ── no ──> reject candidate; retain active snapshot
                    |
                   yes
                    v
           atomically replace active snapshot
```

## What it owns

For each refresh attempt, the runtime keeps an explicit status for every
configured source:

- `valid`: inspection completed and the catalog bindings validate;
- `invalid`: inspection completed but the validator reported one or more
  activation-blocking findings;
- `inspection_failed`: no inspection snapshot was produced. The runtime stores
  a safe structured error instead of a driver exception or credential detail.

The aggregate result is one of:

- `activated`: every configured source is valid, and the candidate becomes the
  active snapshot;
- `rejected`: at least one source is invalid or could not be inspected. The
  candidate is retained in `last_attempt` for diagnostics, but it does not
  replace the prior active snapshot;
- `load_failed`: the three YAML files could not be statically loaded. No
  candidate is created, and any prior active snapshot is retained.

## Building a runtime by hand

`yodb.connect` does this for you. The runtime selects inspection adapters; it does not resolve secrets or
open database connections itself. A PostgreSQL inspector is constructed with a
`PostgresConnectionAdapter`, which owns its bounded connection pool. Then both
the inspector and its validator are registered together for `postgres`:

```python
from yodb.inspection import InspectionAdapterBinding, PostgresCatalogValidator, PostgresSourceInspector, SourceInspectionRegistry
from yodb.runtime import InMemoryCatalogRuntime
from yodb.catalog import SourceKind

postgres_inspector = PostgresSourceInspector(postgres_connections)
inspection_registry = SourceInspectionRegistry([
    InspectionAdapterBinding(
        source_kind=SourceKind.POSTGRES,
        inspector=postgres_inspector,
        validator=PostgresCatalogValidator(),
    )
])

runtime = InMemoryCatalogRuntime("./catalog", inspection_registry)
result = runtime.refresh()

if result.status.value == "activated":
    active_catalog = runtime.active
```

This never writes to a source, infers mappings, or activates a partially
validated catalog. The query engine consumes `runtime.active` only
after activation.
