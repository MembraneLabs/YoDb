---
title: relations.yaml
description: Declare how datasets connect, so that queries can join them.
---

`relations.yaml` declares how datasets connect: a ticket belongs to a customer,
an order has line items. A query can join two datasets only over a relationship
declared here. See [Joins](/query/joins) for how a query uses one.

A relationship names two fields that must be equal. Both fields must already be
mapped in [`sources.yaml`](/catalog/sources); a relationship cannot reach a
column that is not in the catalog.

The file is required, and it must declare at least one relationship. A catalog
with no relationships does not load (`relationships must not be empty`).

```yaml
api_version: yodb/v0.1
relationships:
  customer_has_ticket:
    from: customer
    to: support_ticket
    description: A support ticket belongs to a customer account.
    aliases: [support_case, raised_ticket]
    cardinality: one_to_many
    direction: uni
    implementations:
      - from:
          source: crm_postgres
          field: account_key
        to:
          source: support_postgres
          field: customer_account_key
```

## Relationship attributes

| Attribute | Required | Allowed value | Meaning |
| --- | --- | --- | --- |
| `from` | Yes | Declared dataset name | Origin dataset. |
| `to` | Yes | Declared dataset name | Target dataset. |
| `description` | Yes | String | Business meaning. |
| `aliases` | No | List of strings | Relationship synonyms. |
| `cardinality` | Yes | `one_to_one`, `one_to_many`, `many_to_one`, `many_to_many` | Declared business cardinality. |
| `direction` | Yes | `uni` or `bi` | Traversal direction policy. |
| `implementations` | Yes | Non-empty list | Approved physical ways to resolve it. |

`direction: uni` lets a query go from the `from` dataset to the `to` dataset
only. `direction: bi` lets a query go either way: from a customer to its
tickets, or from a ticket to its customer.

`cardinality` says how many records can be on each side. `one_to_many` here
means one customer has many tickets. It is required, and it is shown to people
and agents so they know whether a join can repeat a row.

## Field-equality implementation

An implementation without `edge_type` compares the two configured endpoint
field values. The endpoints may be in the same PostgreSQL source or different
configured sources.

```yaml
- from: {source: crm_postgres, field: account_key}
  to: {source: support_postgres, field: customer_account_key}
```

This does **not** require a PostgreSQL foreign key. A foreign key may exist and
will be reported by inspection, but the catalog relationship is what explicitly
authorizes YoDb to use the match.

## What a query can follow

A query can follow a relationship when:

- the two fields have the same type (the catalog refuses to load otherwise);
- both fields are public, because YoDb has to read the key.

## Graph edges (not available)

The loader accepts an `edge_type` key on an implementation, meant for a
relationship stored as an edge in a graph database. There is no graph adapter,
so a query cannot follow such a relationship; it is refused with
`query_feature_not_supported`. Leave `edge_type` out.
