---
title: sources.yaml
description: Map approved datasets and fields to read-only physical source locations.
---

`sources.yaml` says where each field lives. It lists your databases, and maps
every field from [`datasets.yaml`](/catalog/datasets) to a table and column in
one of them.

It has two parts. `sources` describes each database. `resolution` then says,
for each dataset, which source supplies each field. `resolution` matters when a
dataset is spread over more than one database.

You do not copy the database's own details here. Column types, indexes and
foreign keys are read from the database when the catalog is validated.

```yaml
api_version: yodb/v0.1
sources:
  crm_postgres:
    kind: postgres
    connection_ref: secret://yodb/crm-readonly
    read_only: true
    datasets:
      customer:
        resource: public.accounts
        identity: [id]
        fields:
          id: {physical_name: account_uuid}
          name: {physical_name: company_name}
          account_key: {physical_name: account_uuid}
resolution:
  customer:
    identity_source: crm_postgres
    field_sources:
      id: crm_postgres
      name: crm_postgres
      account_key: crm_postgres
```

## Source attributes

| Path | Required | Allowed value | Meaning |
| --- | --- | --- | --- |
| `sources.<name>.kind` | Yes | `postgres` | The kind of database. PostgreSQL is the only kind YoDb can read. |
| `connection_ref` | Yes | Non-empty opaque string | Reference resolved outside catalog YAML. |
| `read_only` | Yes | Exactly `true` | V0.1 never writes to a source. |
| `datasets` | Yes | Non-empty mapping | Datasets represented by this source. |
| `datasets.<dataset>.resource` | Yes | Non-empty string | Physical resource name interpreted by the adapter. |
| `identity` | Yes | Non-empty list of mapped field names | Source-local identity claim. |
| `fields` | Yes | Mapping of dataset field to `physical_name` | Approved physical field locations. |
| `physical_name` | Yes | Non-empty string | Exact source column or property. |

For PostgreSQL, `resource` is a table or view with its schema, such as
`public.accounts`, and `physical_name` is a column, such as `account_uuid`.

The loader also accepts `kind: neo4j`, but there is no Neo4j adapter. A catalog
that uses it loads and then fails validation.

## `connection_ref` is not a credential

Use a reference such as `secret://yodb/crm-readonly` or a local-development
reference. A connection resolver turns it into private driver settings at
runtime. Do not place a URL, password, token, or driver option in this file.

The `yodb` command and `yodb.connect` read each reference from the environment
variable `YODB_CONN_<REF>` (see [Quickstart](/getting-started/quickstart)); a
reference such as `crm-readonly` is simplest to name.

The PostgreSQL connection adapter maintains a bounded pool per
`connection_ref`. When all leases are in use, a caller waits until a connection
returns or the configured timeout produces `connection_pool_timeout`.

## Identity and resolution

`identity: [id]` says which of the source's fields identifies one record. YoDb
uses it to match the same record across sources.

A dataset can appear in more than one source. `resolution` then picks, for each
field, the one source that supplies it, and one **identity source** that
decides which records exist. In the sample shop, `crm` is the identity source
for `customer` and supplies most fields, and `billing` supplies `plan`:

```yaml
resolution:
  customer:
    identity_source: crm
    field_sources: {id: crm, name: crm, country: crm, signed_up: crm, plan: billing}
```

A customer with no row in `billing` still appears, with an empty `plan`. A row
in `billing` for a customer that `crm` does not have is ignored.

Rules enforced by the loader:

- `resolution` contains every declared dataset and no unknown dataset.
- `field_sources` contains every declared field for that dataset and no
  unknown field.
- Each listed source must represent the dataset and map the field.
- `identity_source` must map `id`, and its representation must list `id` in
  `identity`.
- Every field in a representation's `identity` must itself be mapped.

During PostgreSQL validation, the physical columns backing the declared
identity must be a primary key or unique constraint.

## Only mapped columns exist

If `public.accounts` also has `billing_contact_email` but it is not in this
file, YoDb cannot expose or use it. Add a declared dataset field and explicit
mapping before it becomes accessible.

## `embeddings`: vectors for the semantic filter

A representation may declare where the vectors of a text field are stored:

```yaml
datasets:
  message:
    resource: support.messages
    identity: [id]
    fields: {id: {physical_name: message_id}, body: {physical_name: body}}
    embeddings:
      body: {column: body_embedding, model: embed-v1, dimensions: 256, metric: cosine}
```

| Path | Required | Meaning |
| --- | --- | --- |
| `column` | Yes | The pgvector column holding the embedding |
| `model` | Yes | The model that produced the stored vectors; must equal the embedding provider's model |
| `dimensions` | Yes | Vector length |
| `metric` | No (`cosine`) | `cosine`, `l2` or `inner_product` |
| `version` | No (`1`) | A label for the embedding run |

The field must be a `string` or `text` field marked `semantic_eligible: true`.
The vectors may sit in the source that owns the text, or in a *vector store*:
a separate source whose representation maps only the dataset identity and
declares the `embeddings`. A field's embeddings are declared once across all
sources. See [Semantic filter](/query/semantic-filter).
