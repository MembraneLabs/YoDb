# Cost-Based Planning: Statistics, Cost Model, and the DP Optimizer

**Status:** implemented and verified (unit tests, a brute-force optimality check,
and a real PostgreSQL run). The fixed-rule planner remains the always-correct
baseline; the optimizer only replaces its choices when it has statistics and
finds a feasible, cheaper plan.

## What it decides

Given a multi-source query (and/or a semantic term) the planner has a correct
plan from fixed rules. The optimizer chooses, from estimates:

1. **The order sources are read in**, for the sources that *bound the result*
   (the anchor and the *required* contributors, i.e. those with a pushed filter).
   Each read may be **restricted** by the IDs learned so far.
2. **Whether enriching (optional) contributors are restricted** by the final ID
   set. They always run last; they never narrow it.
3. **How the semantic term is answered**: verify everything (Plan A), or verify
   a shortlist of K ranked rows (Plan B) with the cheapest K meeting the quality
   requirement.

The chosen order and restrict flags are written into the plan
(`RecordAssembly.schedule`) and the executor follows them. The executor still
checks sizes at run time, so a plan is never wrong because an estimate was.

## Statistics (`planning/statistics.py`)

Three layers; a new database touches only the first.

| Layer | Role |
| --- | --- |
| `StatisticsProvider` (one per source kind) | `statistics(source) -> SourceStatistics \| None`: row count, per-column distinct/null counts, optional min/max, optional latency hints. `None` always means *unknown*. |
| `ObservationStore` | bounded, thread-safe memory of what unrestricted, untruncated scans really returned (exponential moving average, LRU eviction). Keys hold a digest of the filter, never values. |
| `StatisticsService` | resolves *observation > provider > default > unknown*; the only thing the planner calls. Provider errors are swallowed into "unknown" (a statistics failure must never fail a query). |

`PostgresStatisticsProvider` reads `pg_class.reltuples` and `pg_stats`
(`n_distinct`, `null_frac`) with two small catalog queries, cached per table
(including cached failures), `last_error` holds only the exception class name.
`reltuples = -1` (never analyzed) is unknown. Min/max are not read, so range
selectivity uses the flat default.

`estimate_selectivity` (generic, adapter-independent): equality `non_null/ndv`,
`IN`, `NOT IN`, `NE`, null tests from the measured fraction, ranges interpolated
between known bounds, combinators assuming independence (`AND` product, `OR`
`1-Π(1-s)`, `NOT` `1-s`), flat defaults when statistics are missing, and a floor
of one row for any filter not provably empty.

## Cost model (`planning/optimizer.py`)

Objective: `latency_ms + money_weight × money` (`money_weight` default 1000).

* **Plain read**, unrestricted: `call + rows × per_row`, infeasible if the
  expected rows exceed the source's row cap (it would fail at run time).
* **Restricted read** (needs the source's `key_lookup`, and the ID set within
  `min(planner bound, source limit)`): `call + keys × per_key + rows × per_row`
  with `rows = keys × pass_fraction`.
* **Ranked (Plan B) anchor read**: only valid as the *last* result-bounding read
  and, when required contributors exist, only *restricted* by them, so the
  shortlist is cut after the required matches (see "Safety" below). Adds a
  per-row ranking cost; returns `min(K, pool)` rows.
* **Semantic step**: calls = `ceil(verified / batch)`, `verified =
  min(pool, page_size / expected_selectivity)` (a page that fills early stops
  early); Plan A is infeasible when the pool exceeds `maximum_candidates`.
  Plan B adds an embedding call and must meet the required recall.
* **Recall** is a pluggable `RecallModel` (default `PowerLawRecall`:
  `(K/pool)^0.5`). The bar is the caller's `minimum_quality`, else
  `minimum_expected_recall` (0.8).
* **Approximation margin**: Plan B is approximate, so it must beat the exact
  plan by `shortlist_min_saving` (20%) to be preferred; not applied when verify-all
  is infeasible.
* **Hard limits**: `maximum_cost` and `maximum_latency_ms` prune any candidate
  estimated to break them.
* Provider `cost_hint` (`ProviderCost`) and the runtime batch size feed the model;
  unspecified values use `CostParameters` defaults.

## Why DP, and how it stays small

Under independence, the IDs known after reading a *set* of sources do not depend
on the order, so the cheapest way to have read a set is the cheapest way to have
read a smaller set plus the last read: DP over subsets, `2^m × m` instead of
`m!`. Semantic verification cost depends only on the final candidate count, and
Plan B is one extra transition (anchor last), so the semantic term does not
break the recurrence. Capped by `maximum_dp_sources` (10).

Per-step restrict/plain is chosen independently (it depends only on the incoming
ID estimate), so flags are never enumerated. Ties are resolved toward the
planner's own rule plan: the optimizer deviates only when strictly cheaper.

## When it declines (the fixed-rule plan is kept; the reason is in `explain`)

`PlanExplanation.optimizer` is `strategy=cost_based …estimates…` or
`strategy=rules reason=…`:

* no statistics service configured;
* any participating source's size unknown (provider missing/failing/never analyzed);
* more result-bounding sources than `maximum_dp_sources`;
* no candidate estimated feasible (row caps, candidate cap, recall bar, money or
  latency limits). Planning never fails on an *estimate*; run-time guards enforce.

An explicit `preference` (`verify_all` / `vector_shortlist`) is never overridden
by cost.

## Safety fix found along the way

A shortlist cut *before* the required contributors narrowed the anchor could
return fewer than a page of true matches. A ranked anchor read is now valid only
after every required contributor has narrowed it and only when restricted by
their IDs; otherwise the executor falls back to a plain guarded scan and Plan A
verification, and the result stats report `verify_all`.

## Learning

After each execution the engine feeds every complete, unrestricted, untruncated
scan back via `StatisticsService.observe`. Restricted, limited and ranked scans
are not learned from (their size reflects the restriction, not the source). An
observed filtered size overrides the provider's estimate for that exact filter.

## Extending it

| To add… | Touch only… |
| --- | --- |
| a database's statistics | a `StatisticsProvider` registered for its kind |
| a different recall assumption | a `RecallModel` passed in `CostParameters` |
| provider cost realism | `cost_hint` on the provider, or `CostParameters` |
| a new cost term (e.g. bytes moved) | `Problem.plain_read`/`ranked_read` (one function each); the DP and the brute-force test share it |
| another semantic variant | a branch in `optimize` plus `Problem.semantic_estimate` |

## Verified by

* `tests/test_optimizer.py`: the DP's optimum equals a brute-force search over
  every order, restrict choice and semantic variant on 400 random instances,
  including infeasible ones; the reported estimate equals the chosen plan's cost.
* `tests/test_statistics.py`, `tests/test_cost_based_planning.py`,
  `tests/test_assembly_schedule.py`: selectivity, observations, provider, plan
  deviation and decline, learning, schedule following, shortlist safety.
* `tests/e2e` cases `O1`–`O4` on PostgreSQL + pgvector with real `pg_stats`:
  O1/O2 fail under the fixed rules (the huge filter exceeds the row guard) and
  succeed under the cost-based plan reading ~400 rows; O3 declines and fails safe.

## Known limits

* Independence between filters/sources is assumed; correlated data will mislead
  estimates (run-time restriction and learned sizes soften this).
* Estimates for unrestricted-but-filtered scans use column statistics only; no
  histograms or most-common values.
* Costs are in assumed units until providers publish hints; latency per call is a
  default unless a provider reports it.
* The default recall model is a guess, not fitted to data (benchmark work).
* No parallel scheduling: independent scans are costed as sequential.
