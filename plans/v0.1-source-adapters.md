# Adding a Database: the Source Adapter Contract

A new database is added by writing an **adapter** and declaring what it can do.
The planner and executor never branch on a database's name; they read the
adapter's declaration and plan accordingly. A source that declares less simply
gets less pushed down and more done in YoDb, so declaring conservatively is
always safe. **Declaring more than the compiler preserves exactly is a bug.**

## What to write (one source kind)

| Piece | Responsibility |
| --- | --- |
| `SourceCapabilities` + `CapabilityPlanningAdapter(capabilities)` | the declaration; pushdown decisions are derived from it, so there is no pushdown code to write |
| `QueryCompilerAdapter.compile_scan(RemoteScan)` | turn one planner-approved fragment into the native command; must honor `key_filter` and `vector_search` if declared |
| `QueryExecutionAdapter.execute` | run the command, return rows keyed by logical field name |
| connection adapter, `SourceInspector`, `SourceCatalogValidator` | connect, and confirm tables match the catalog |

Register each in its registry. Nothing in `planner.py` or `federated.py` changes.

## `SourceCapabilities`: what each field makes the planner do

| Field | Planner behavior |
| --- | --- |
| `filter_operators`, `filterable_types` | a predicate is pushed only if its operator **and** field type are declared; otherwise it stays in YoDb, with the reason in the decision |
| `boolean_operators` (`all`/`any`/`not`) | a compound filter is pushed only if every combinator it uses is declared |
| `supports_order`, `orderable_types` | order is pushed only when declared for every order field |
| `supports_limit` | a limit is pushed only with its order (a source that limits must also order) |
| `text_ordering` | `SOURCE_DEFINED`: a single source's order is trusted; when YoDb orders text across sources (code-point order) the explain carries a note naming sources whose collation differs |
| `maximum_rows` | row guard per scan is `min(planner policy, this)` |
| `key_lookup` (`maximum_keys`) | the scan may be restricted to a logical-ID set no larger than this; no declaration means it is never restricted, and results stay correct |
| `vector_search` (`metrics`, `combines_with_filters`, `maximum_shortlist`) | a shortlist (Plan B) is considered only if declared, only for a supported metric, only with other filters if `combines_with_filters`, and never larger than `maximum_shortlist` |

PostgreSQL's declaration is `POSTGRES_CAPABILITIES` in `planning/postgres.py`.
`contains`/`starts_with` are deliberately undeclared (case/collation semantics
are not pinned down), so they run in YoDb.

## How it is kept honest

- `tests/test_source_capabilities.py` registers a deliberately weak fake database
  (eq/in on strings only, no order or limit, no ID restriction, no vector search)
  and shows the planner adapting with no planner change.
- A Postgres conformance test pushes every operator and boolean combinator the
  declaration lists and compiles it; undeclared operators must not be pushed.
  A new adapter should add the same kind of test for its own declaration.

## What an adapter shows

`operator_support(capabilities)` and `describe_capabilities(capabilities)` list every
operator in the catalog ([v0.1-operators.md](v0.1-operators.md)) with whether the
database runs it (`source`), YoDb runs it (`coordinator`) or it is `unavailable`,
and the strategies that makes legal. They are derived from the declaration, so they
cannot drift from what the planner does.

## Statistics (optional, per source kind)

An adapter may also register a `StatisticsProvider` (see
[v0.1-cost-based-planning.md](v0.1-cost-based-planning.md)). With none, the
planner keeps its fixed rules for plans touching that source and `explain` says
which source lacked statistics. `PostgresStatisticsProvider` is the reference.

## Not adapter-driven yet

- **Vectors stored apart from the records.** Plan B assumes the embedding column
  is in the same source representation as the text (the catalog's `embeddings`
  binding lives there). A dedicated vector store holding only vectors would need
  a cross-source shortlist (rank in the vector source, then restrict the record
  source by IDs). The capability description is already enough for a vector
  database that holds the records itself.
- **Hand-written cost hints.** Row counts and column statistics come from the
  provider; per-call latency is a default unless the provider reports it.
- **Transfer strategy.** "Required contributors first, then restrict by IDs" is
  fixed in the executor; an adapter cannot say its full scan is cheap or its ID
  lookup expensive.
- **Source-reported collation details** beyond `text_ordering`.
