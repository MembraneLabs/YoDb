# Vector store as a separate source (v0.1)

The embeddings of a text field may live in a **different source** (a different database or server) from
the text. The catalog says where; the planner and executor do the rest.

## Catalog

```yaml
sources:
  vectors:                       # a separate server
    kind: postgres
    connection_ref: vectors
    datasets:
      message:
        resource: vec.message_vectors
        identity: [id]
        fields: {id: {physical_name: message_id}}      # identity only: the text is owned elsewhere
        embeddings:
          body: {column: embedding, model: potion-base-8M, dimensions: 256, metric: cosine}
```

Rules: a representation holding embeddings for a field it does not map must map the dataset identity; one
text field's embeddings are declared once, across all sources.

## Plan

1. Required contributors are read first (as before).
2. **Shortlist**: the vector store returns the K IDs nearest the embedded proposition, ranked among the IDs
   learned so far when they fit the store's key limit, else among all of its vectors.
3. The anchor (and enrichers) are read only for those K IDs, then verified.

Schedule roles: `required*`, `shortlist`, `anchor`, `optional*`. The shortlist step carries no fields; it
narrows later reads and is a match requirement (only shortlisted records survive). K is bounded by the
anchor's key limit and the transfer policy, so the anchor read is always restrictable.

Eligibility mirrors the same-source shortlist (embedder matches the declared model/dimensions, metric
supported, every filter enforced by its source) plus: the anchor must be restrictable by IDs and key
transfer must be on. Otherwise the plan verifies everything and says why.

## Cost and recall

The optimizer treats the store as a source of role `SHORTLIST`; a store variant demands "rank in the store
after the required sources, then read the anchor for the K IDs". Pool and recall depend on whether the
required IDs fit the store's key limit (ranked among them) or not (ranked among everything, then
intersected, which loses recall).

## What the real-data run showed (BANKING77, 13,083 messages, 256-dim open model)

* Verify-all equals the SQL oracle on every query; the shortlist never returned a non-match.
* The shortlist is a **post-filter** for filters on the anchor: with a filter that leaves 11% of the corpus,
  a shortlist of 1,000 finds about half of the true matches. Filters on contributors do better (their IDs
  restrict the store) as long as they fit the key limit.
* The planner's default recall curve `(K/N)^0.5` was far too pessimistic for this model (assumed 28% at
  K=1000, measured 71%), so the cost-based planner kept declining. A curve fitted to the model (exponent
  about 0.15) lets it choose: recall 0.93-1.00, every page filled, 60-65% less verification where a
  shortlist is chosen.
* Fixed: the Postgres statistics provider cached only the columns of the first query that touched a table;
  later filters on other columns got a default selectivity. It now caches the whole table and reads
  most-common-value frequencies, so skewed columns estimate well.

## Not built yet

* **Rank after the anchor filter** (read the filtered anchor first, then rank among its IDs): the fix for
  the post-filter recall loss when the anchor filter is selective.
* A recall curve learned from calibration queries instead of a one-parameter power law (the fitted curve is
  optimistic at small K).
* An approximate (HNSW) index: the tie-break on the ranking query makes Postgres use an exact scan.
