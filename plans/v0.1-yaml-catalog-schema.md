# YoDb V0.1 YAML Catalog Schema

## Purpose

This document defines the first executable V0.1 catalog format. It is the
controlling user-authored YAML contract for the catalog loader.

The catalog is intentionally only three files:

```text
datasets.yaml   business-level datasets and fields
sources.yaml    connected sources plus physical dataset/field locations
relations.yaml  logical relationships and their physical implementations
```

There are no per-table files, per-relationship files, or user-authored named
mapping objects. A source directly says which datasets it contains.

```text
dataset -> source -> resource -> physical field
```

For example:

```text
customer -> crm_postgres -> public.accounts -> account_uuid
```

The same YAML structure describes PostgreSQL, Neo4j, and future adapters. The
adapter interprets `resource` and `physical_name` according to `source.kind`.

| Source kind | `resource` | `physical_name` |
| --- | --- | --- |
| `postgres` | Schema-qualified table or view | Column |
| `neo4j` | Node label | Node property |
| Future `mongo` | Collection | Document path |

V0.1 implements only `postgres` and `neo4j` source kinds. `neo4j` catalog
parsing is supported; source inspection/execution arrives in its graph
milestone.

## Common rules

- Every document has `api_version: yodb/v0.1`.
- Logical names, source names, dataset names, field names, and relationship
  names use lower snake case: `^[a-z][a-z0-9_]*$`.
- YAML contains a `connection_ref`, never credentials themselves.
- The catalog is closed-world: an unmentioned physical resource or field is
  inaccessible for all YoDb operations.
- `visibility: internal` fields are mapped and can support approved identity
  and relationship execution but cannot be returned, filtered, ordered, or
  searched by normal callers.
- A catalog load performs static cross-file validation only. Connection,
  physical-resource existence, physical type, uniqueness, and join-coverage
  validation belong to source inspection/profiling later in Milestone 1.

## `datasets.yaml`

This file contains no database, table, label, property, or column names.

```yaml
api_version: yodb/v0.1

catalog:
  name: acme_data
  version: 1

datasets:
  customer:
    description: A company with a commercial account.
    aliases: [client, account, organization]

    fields:
      id:
        type: id
        description: Stable customer identity.

      name:
        type: string
        description: Customer company name.
        aliases: [company, organization_name]

      plan_tier:
        type: string
        description: Current commercial subscription level.
        example_values: [enterprise, business, starter]

      crm_account_key:
        type: uuid
        description: CRM key used for approved joins.
        visibility: internal

  support_ticket:
    description: A customer support case and its conversation.

    fields:
      id:
        type: id
        description: Stable ticket identity.

      customer_crm_key:
        type: uuid
        description: CRM customer key used for approved joins.
        visibility: internal

      content:
        type: text
        description: Customer support conversation and issue description.
        semantic_eligible: true
```

### Required schema

| Path | Required | Meaning |
| --- | --- | --- |
| `catalog.name` | Yes | Catalog identifier. |
| `catalog.version` | Yes | Positive immutable catalog version. |
| `datasets.<dataset>.description` | Yes | Business meaning. |
| `datasets.<dataset>.fields` | Yes | One or more fields. |
| `fields.<field>.type` | Yes | `id`, `string`, `text`, `int`, `float`, `bool`, `timestamp`, `uuid`, `json`, or `bytes`. |
| `fields.<field>.description` | Yes | Human-readable business meaning. |
| `fields.<field>.visibility` | No | `public` by default, or `internal`. |
| `fields.<field>.aliases` | No | Business synonyms. |
| `fields.<field>.example_values` | No | Safe examples/enumeration values. |
| `fields.<field>.semantic_eligible` | No | `false` by default. |

Every dataset must declare a public logical `id` field whose type is `id`.

## `sources.yaml`

This file declares read-only source connections, direct logical-dataset
representations, and which source supplies each field.

```yaml
api_version: yodb/v0.1

sources:
  crm_postgres:
    kind: postgres
    connection_ref: secret://yodb/crm-readonly
    read_only: true

    datasets:
      customer:
        resource: public.accounts
        identity: [id]
        fields:
          id: { physical_name: account_uuid }
          name: { physical_name: company_name }
          plan_tier: { physical_name: subscription_level }
          crm_account_key: { physical_name: account_uuid }

  support_postgres:
    kind: postgres
    connection_ref: secret://yodb/support-readonly
    read_only: true

    datasets:
      support_ticket:
        resource: public.tickets
        identity: [id]
        fields:
          id: { physical_name: ticket_id }
          customer_crm_key: { physical_name: crm_account_uuid }
          content: { physical_name: body }

  relationship_graph:
    kind: neo4j
    connection_ref: secret://yodb/graph-readonly
    read_only: true

    datasets:
      customer:
        resource: Customer
        identity: [crm_account_key]
        fields:
          crm_account_key: { physical_name: crmAccountUuid }

resolution:
  customer:
    identity_source: crm_postgres
    field_sources:
      id: crm_postgres
      name: crm_postgres
      plan_tier: crm_postgres
      crm_account_key: crm_postgres

  support_ticket:
    identity_source: support_postgres
    field_sources:
      id: support_postgres
      customer_crm_key: support_postgres
      content: support_postgres
```

### Required schema

| Path | Required | Meaning |
| --- | --- | --- |
| `sources.<source>.kind` | Yes | `postgres` or `neo4j`. |
| `sources.<source>.connection_ref` | Yes | Non-secret reference to external connection configuration. |
| `sources.<source>.read_only` | Yes | Must be `true` in V0.1. |
| `sources.<source>.datasets` | Yes | Logical datasets represented by that source. |
| `datasets.<dataset>.resource` | Yes | Physical table/view/label, interpreted by adapter. |
| `datasets.<dataset>.identity` | Yes | One or more mapped fields forming the source-local identity. |
| `datasets.<dataset>.fields` | Yes | Mapped field to physical name mapping. |
| `resolution.<dataset>.identity_source` | Yes | Source that supplies the dataset identity. |
| `resolution.<dataset>.field_sources` | Yes | Source that supplies every declared field. |

A source may represent many datasets and a dataset may appear under many
sources. V0.1 permits only one representation of a given dataset in a
given source; this removes the need for user-authored mapping names.

## `relations.yaml`

This file defines logical relationships plus one or more physical ways to
resolve them.

```yaml
api_version: yodb/v0.1

relationships:
  customer_has_ticket:
    from: customer
    to: support_ticket
    description: A support ticket associated with a customer.
    aliases: [support_case, raised_ticket, complaint]
    cardinality: one_to_many

    implementations:
      - kind: key_match
        from:
          source: crm_postgres
          field: crm_account_key
        to:
          source: support_postgres
          field: customer_crm_key

      - kind: edge
        source: relationship_graph
        edge: HAS_TICKET
        direction: out
```

### Required schema

| Path | Required | Meaning |
| --- | --- | --- |
| `relationships.<name>.from` | Yes | Origin dataset. |
| `relationships.<name>.to` | Yes | Target dataset. |
| `relationships.<name>.description` | Yes | Business meaning. |
| `relationships.<name>.cardinality` | Yes | `one_to_one`, `one_to_many`, `many_to_one`, or `many_to_many`. |
| `relationships.<name>.implementations` | Yes | One or more approved physical implementations. |
| `key_match.from/to` | Yes | Source and mapped field for each endpoint. |
| `edge.source` | Yes | Neo4j source containing both endpoint datasets. |
| `edge.edge` | Yes | Exact physical relationship type. |
| `edge.direction` | Yes | `out` or `in` relative to `from`. |

`key_match` supports the first relational join implementation. `edge` describes
one Neo4j graph-edge implementation. The loader validates both shapes but the
runtime can return `capability_unavailable` until that backend implementation is
delivered.

## Loader validation

The loader rejects a catalog when any of these is true:

- a document has a wrong version, missing required value, unknown key, or
  invalid identifier;
- a source references an undeclared dataset or field;
- a source representation uses an unmapped identity field;
- a source is not explicitly read-only;
- a resolution is missing, references a nonexistent source, or assigns a field
  to a source that does not map that field for that dataset;
- a relationship references undeclared datasets, sources, or fields;
- a `key_match` endpoint is not mapped in the correct dataset under its source;
- an `edge` implementation uses a non-Neo4j source or a Neo4j source that does
  not represent both endpoint datasets.

The resulting in-memory `Catalog` is immutable and contains only validated
logical metadata. It does not connect to a database.
