# V0.1 SemanticFilter: Contract and Plan

**Status:** contract **and baseline execution** implemented: Plan A (verify
all) and Plan B (pgvector shortlist) run end to end against PostgreSQL +
pgvector with injected embedding and verification providers, per-record
provenance and per-query stats. Plan choice is a fixed eligibility rule, not a
cost estimate; statistics-driven choice, live pgvector validation, real
providers and the benchmark are not built.

This supersedes the "Semantic search" section of
[v0.1-query-model.md](v0.1-query-model.md), which described a ranked,
candidate-producing `semantic:` block. The controlling
[V0.1 plan](v0.1-federated-semantic-data-layer.md) defines the operator as a
*filter*, and this document follows it.

## Meaning

`SemanticFilter(field, proposition)` asks: **is the proposition true of this
record's text?** It is a Boolean condition like any other filter term. It does
not rank, score, or order results. Vector similarity is only one way to find
candidates cheaply; it is never part of the meaning. Callers never name
pgvector, an index, an embedding model, SQL, or a provider.

## Query syntax

A new leaf in the `where` tree:

```yaml
from: {dataset: ticket}
select: [subject]
where:
  all:
    - {field: priority, op: gte, value: 3}
    - semantic:
        field: body
        proposition: The customer is seriously considering cancelling primarily because of price
constraints:
  minimum_quality: 0.8      # only valid when the query has a semantic condition
```

A top-level `semantic:` key outside `where` is rejected with a pointer here.

## Binding rules (enforced, tested)

| Rule | Error |
| --- | --- |
| field exists and is public | `field_not_found` / `field_not_accessible` |
| field type is `string` or `text` | `query_operator_not_supported` |
| field is `semantic_eligible: true` in the catalog | `query_operator_not_supported` |
| proposition is non-blank and ≤ 1,000 chars (policy) | `query_shape_invalid` / `query_value_type_invalid` / `query_limit_invalid` |
| at most **1** semantic condition per query (policy `maximum_semantic_filters`) | `query_limit_invalid` |
| only in **conjunctive position**: the whole `where`, or under `all` (nested `all` is fine) | `query_expression_invalid` under `any`/`not` |
| `constraints.minimum_quality` requires a semantic condition and must be ≤ 1 | `query_limit_invalid` |

Why conjunctive only: a proposition can be answered cheaply only by narrowing
candidates with the other terms and then verifying. Under `any`/`not` the full
set of records satisfying the proposition would be needed, so V0.1 refuses
instead of approximating silently. The query fingerprint includes the trimmed
proposition, so a cursor or session can never be reused for a different one.

## Catalog metadata

An optional, per-source-representation vector binding for a text field:

```yaml
datasets:
  ticket:
    resource: public.tickets
    identity: [id]
    fields: {id: {physical_name: id}, body: {physical_name: body}}
    embeddings:
      body: {column: body_embedding, model: embed-v1, dimensions: 1536, metric: cosine, version: "2"}
```

`metric` is `cosine | l2 | inner_product`. Validated statically: the field must
be mapped in the same representation, `semantic_eligible`, and `string`/`text`;
`dimensions > 0`; column/model/version non-blank. Embeddings are optional: with
none, only Plan A is possible. Live validation (the vector column exists with
those dimensions) belongs to the PostgreSQL inspector and is not built yet.

## Providers (`yodb.semantic`)

Injected like database adapters; nothing here names a vendor.

- `EmbeddingProvider.embed(EmbeddingRequest) -> EmbeddingResult`: query-side
  vectors. Its `info.model` and `dimensions` must equal the catalog binding
  being searched; a mismatch is a planning error, never a cross-space compare.
- `PropositionVerifier.verify(VerificationRequest) -> VerificationResult`: a
  bounded batch of `(logical_id, text)` → one `VerificationVerdict(holds,
  confidence?)` each, plus measured `VerificationUsage` (calls, tokens, cost,
  latency) and `ProviderInfo` (provider, model, version).
  `VerificationResult.require_complete_for` rejects a verifier that skips,
  duplicates, or invents a candidate.

## Quality rule

`passes_quality(verdict, minimum_quality)`: a record qualifies **only on a
positive verdict**; with `minimum_quality` set, that verdict's confidence must
reach it, and a positive verdict reporting no confidence counts as 1.0. A
confident "no" is still no. So raising the bar can only shrink the result.

## Result metadata

Per record: `SemanticRecordMetadata(plan, holds, confidence, provider/model/
version)`. Per query: `SemanticExecutionStats(plan, candidates_considered,
shortlisted, verified, qualified, usage, embedding_model_calls)` with the
invariant `qualified ≤ verified ≤ candidates_considered`; these feed the
estimate-versus-actual telemetry.

## Physical plans (implemented)

```text
Plan A  VERIFY_ALL        SQL filters -> verify candidates in the caller's order
Plan B  VECTOR_SHORTLIST  SQL filters + pgvector top-K (one scan) -> verify the shortlist
```

Both are one `SemanticVerify` node over the records the normal planner produces
for the rest of the query (the semantic term is removed from the filter first).

- **Early stop (both plans).** Candidates are ordered by `order_by` and verified
  in batches until `page.first` qualify. The page is the first N qualifying
  records in order, so this returns exactly what verifying everything would.
- **Bounds.** At most `maximum_candidates` (default 1,000) records reach the
  verifier; more is `query_semantic_budget_exceeded`, with no model call.
  `constraints.maximum_cost` and `maximum_latency_ms` are checked between
  batches. Records without text are never verified and never returned.
- **Plan B eligibility (all required, else Plan A with a `note:` in explain):**
  an embedding provider whose model and dimensions equal the catalog binding;
  the text field owned by the identity source with an `embeddings` binding; the
  source declares `vector_search` for that metric (and `combines_with_filters`
  unless the query has no other filter; see
  [v0.1-source-adapters.md](v0.1-source-adapters.md)); and every other filter term is enforced by its
  source (otherwise the shortlist would be taken *before* a filter that runs
  later in YoDb). `preference: vector_shortlist` turns ineligibility into an
  error. Shortlist size is `max(minimum_shortlist, page x oversample)` capped by
  `maximum_candidates`.
- **SQL.** The shortlist is the identity source's own scan with
  `AND col IS NOT NULL ORDER BY col <op> $vector, id LIMIT K`, under the same
  filters and any key restriction from required contributors (cosine `<=>`, L2
  `<->`, inner product `<#>`). The embedded query vector is filled in at run
  time; the planner never embeds.
- **Results.** `QueryExecutionResult.semantic` holds per-query stats (plan,
  considered, shortlisted, verified, qualified, calls, tokens, cost, embedding
  calls) and per-returned-record provenance.

**Plan B is approximate.** It returns only true matches (every record is
verified), but its page is "the first N matches among the K nearest", which can
differ from Plan A's page and can miss matches ranked below K. That is the cost
of the saving, and why `minimum_quality`, budgets and the shortlist size matter.

## Remaining work, in order

1. **Live validation** that an `embeddings` column exists with the declared
   dimensions (and that pgvector is installed) in the PostgreSQL inspector.
2. **Statistics hook + cost-based choice** between A and B (cardinality after
   SQL filters, expected recall, model-call and cost budgets); explain both.
3. **Real providers** behind `EmbeddingProvider` / `PropositionVerifier`, with
   retries, timeouts and cost accounting.
4. **Labeled benchmark** showing Plan B cuts model calls/cost/latency vs Plan A
   at the agreed quality on a large table (the V0.1 thesis). On a table smaller
   than the shortlist the two plans verify the same records, so no saving shows.
5. **Semantic fields owned by a contributor source** (today forces Plan A), and
   `allow_partial_results` for provider failure (today fails closed).

## Decisions made here (revisit if wrong)

- One semantic condition per query, conjunctive position only.
- Boolean semantics with optional per-verdict confidence; `minimum_quality` is a
  confidence floor on positive verdicts, not a similarity threshold.
- Semantic queries return filter results ordered like any other query; there is
  no relevance ordering in V0.1.
- Cursors stay unsupported (already rejected); semantic search-session cursors
  remain a later contract.
