# V0.1 Federated Planner: Design and Implementation Plan

> **Update:** cost-based choice of read order, key restriction and the semantic
> plan is implemented; see [v0.1-cost-based-planning.md](v0.1-cost-based-planning.md).

**Status:** baseline P0–P4 implemented for PostgreSQL on the
`codex/federated-planner` branch. The baseline proves the complete logical
query → physical plan → source execution → coordinator result path. Bounded
logical-ID key transfer is implemented as an adaptive execution strategy
(selective required contributors first, each restricting later scans with
`id IN (...)`, sent in batches of up to `maximum_transfer_keys` for up to
`maximum_key_batches` reads, otherwise a plain guarded scan; an empty key set stops
the query). Cost-based read ordering (`v0.1-cost-based-planning.md`) and joins between
datasets (`v0.1-operators.md`) were added after this baseline. Parallel scheduling
remains later work.

## Decision

Build a real **federated physical planner** before expanding the cost package.

The planner receives a validated logical query and an active catalog snapshot.
It produces one or more **executable, semantics-preserving physical DAGs**.
Every source-local operation in that DAG must be compilable by a registered
adapter, and every coordinator operation must be implementable by YoDb's
executor.

Only after the planner can produce several executable alternatives should the
cost model estimate them, policy admit/reject them, and a chooser select one.

```text
caller
  │ logical query: datasets, public fields, declared relationships
  ▼
parse + bind + source resolution                 already exists
  ▼
FEDERATED PLANNER                                build this first
  │ physical DAGs that are valid and executable
  ▼
compiler validation                              build with planner
  │ parameterized source-native remote operations
  ▼
executor                                         baseline before optimization
  │ actual source reads + coordinator assembly
  ▼
cost estimator / policy / chooser                integrate only afterward
```

Before this implementation, `src/yodb/planning` was not this planner. It contained
some useful names and a partial candidate sketch, but it does not yet drive
the engine, prove compiler support, produce execution-ready fragments, or
provide an executable DAG. Treat it as a prototype to redesign around this
document, rather than a completed planner. The baseline now implements the
contracts, PostgreSQL fragment compiler, plan-driven engine, explain output,
and bounded in-memory assembly described below.

## Why planning comes before costing

A cost estimator may only compare plans that are both:

1. **semantically valid** — they return the same logical result; and
2. **executable** — every node has an adapter/compiler/executor implementation.

Without that rule, cost estimates are guesses about plan-shaped objects that
cannot actually run. That is what happened in the first cost-model increment:
it could mark a filter as “pushed” but the central execution engine never
consumed the physical plan, so no pushed SQL was run.

The planner establishes the contract that fixes this:

```text
logical meaning
      │
      ├── planner validates each rewrite preserves meaning
      ├── compiler validates each remote fragment is implementable
      └── executor validates every physical node has a runtime implementation
```

The cost model then compares *valid alternatives*, rather than deciding what
is valid.

## Research principles applied to YoDb

### 1. Logical plans and physical plans are different things

PostgreSQL explores lightweight path representations before producing the
detailed plan its executor can run. It attaches filters and projections to the
appropriate plan nodes while considering alternatives.
[PostgreSQL planner/optimizer](https://www.postgresql.org/docs/17/planner-optimizer.html)

Neo4j similarly moves from a declarative graph query through a logical plan to
a physical plan executed by its runtime.
[Neo4j execution-plan lifecycle](https://neo4j.com/docs/cypher-manual/25/planning-and-tuning/execution-plans/)

For YoDb:

- the existing `BoundQuery` is the logical request;
- `SourceResolvedQuery` is a logical ownership/binding analysis;
- the new planner output is a physical DAG of remote and coordinator work;
- compiled SQL/Cypher/etc. is source-native execution detail, not the plan
  itself.

### 2. Rewrite rules own correctness; the optimizer owns comparison

Calcite separates equivalence-preserving planner rules from the mechanism that
chooses among transformed alternatives. Adapters expose counterparts for only
the operators their engine can execute; unsupported work stays in the engine's
fallback convention.
[Calcite adapters, rules, and calling conventions](https://calcite.apache.org/docs/adapter)

YoDb will follow the same split in a deliberately smaller form:

- **rewrite rules** decide whether a filter, projection, order, limit, or
  relationship operation can move into a source fragment;
- **adapter capabilities** decide whether that source can preserve the required
  semantics;
- **costing** later compares valid fragment/DAG arrangements;
- **coordinator nodes** are the fallback for work no source can safely do.

### 3. Pushdown is adapter-specific and must be observable

Trino lets connectors accept or refuse specific filter, projection, limit,
Top-N, aggregation, and join pushdowns. Its plan/explain output reflects what
remained in the engine after pushdown.
[Trino connector pushdown contract](https://trino.io/docs/current/develop/connectors.html)
[Trino pushdown behavior](https://trino.io/docs/current/optimizer/pushdown.html)

YoDb needs the same observable outcome: a physical-plan explanation must make
it obvious which predicate entered which remote fragment, which predicate
remained in YoDb, and why.

### 4. Candidate search must be bounded

PostgreSQL switches away from near-exhaustive join enumeration when join count
makes planning expensive. [PostgreSQL planner search](https://www.postgresql.org/docs/17/planner-optimizer.html)

YoDb V0.1 must be much stricter. It has declared relationships, a small query
language, and a hard maximum traversal depth. It should enumerate templates
for source boundaries, not all permutations of native database access paths
or arbitrary joins.

### 5. Dynamic/key filtering is a runtime dependency, not a free rewrite

Federated systems can collect keys from a selective branch and use them to
filter a dependent branch; Trino calls this dynamic filtering. It reduces
source/network load but is connector-specific and requires bounds on collected
values. [Trino dynamic filtering](https://trino.io/docs/current/admin/dynamic-filtering.html)

In YoDb, this becomes an explicit `KeySet → KeyLookup` dependency in the
physical DAG. It may not be represented as two independent scans, and it may
not execute until the key set has passed its runtime bound.

## Scope and non-goals

### V0.1 planner scope

- One root logical dataset.
- One or more declared representations of that dataset across sources.
- Logical record assembly by the configured stable logical `id` only.
- Public field projection, Boolean filtering, deterministic ordering, and
  keyset-page preparation from the existing query model.
- PostgreSQL as the only implemented remote compiler/executor adapter.
- Source-local filter and projection pushdown where semantic equivalence is
  established.
- Baseline multi-source execution in YoDb memory with explicit bounds.
- Plan/explain artifacts that contain only logical names and configured source
  aliases, never credentials or user-controlled native text.

### Explicitly deferred

- Source-native join execution (the implemented join runs in YoDb) and same-source relation candidates.
- Reverse key-transfer execution.
- Parallel scheduler and cancellation fan-out.
- (Done since: key transfer, in batches; cost-based choice among plans; joins between datasets.)
- Aggregates, windows, CTEs, raw SQL/Cypher, arbitrary functions.
- Semantic search and graph traversal execution; their physical-node hooks are
  designed here but they are implemented later.
- Distributed transactions, writes, temporary tables, source mutation, and
  automatic index creation.

The key point: **baseline planning and execution are not optional**. They are
what makes later cost optimization testable.

## Planner ownership and boundaries

| Component | Owns | Must not own |
| --- | --- | --- |
| query parser/binder | caller shape, logical field/type checks, catalog fingerprint | physical source decisions |
| source resolver | approved field ownership, logical-ID links | pushdown, SQL, candidate choice |
| planner | physical DAG, rewrite legality, required plan properties, bounded alternatives | raw SQL/Cypher, index choice, connection lifecycle |
| adapter capability provider | semantics it can preserve for a requested fragment | business mapping inference or cost-policy choice |
| compiler | parameterized native command for one validated remote fragment | logical query validation or cross-source assembly |
| executor | run selected DAG, materialize/stream coordinator nodes, enforce runtime guards | deciding source placement |
| cost model | estimate complete executable candidate DAGs | inventing rewrites or executing queries |
| policy/chooser | reject unsafe candidates and choose among admitted candidates | changing query semantics |

## Planner input and output

### Input

```python
plan = planner.plan(
    resolved_query: SourceResolvedQuery,
    active_catalog: CatalogEvaluation,
    capabilities: SourceCapabilityRegistry,
    planner_policy: PlannerPolicy,
)
```

The planner accepts only `SourceResolvedQuery` tied to the exact active catalog
fingerprint. It must reject a resolution/capability mismatch rather than
falling back to unapproved source access.

### Output

For the baseline milestone, output exactly one `ExecutablePlan` or a typed
planning error. Do **not** return speculative alternatives yet.

```python
@dataclass(frozen=True)
class PlannedQuery:
    plan: ExecutablePlan
    catalog_fingerprint: str
    query_fingerprint: str
    explain: PlanExplanation


ExecutablePlan = RemotePlan | CoordinatorPlan
```

Later, after baseline execution passes E2E tests:

```python
@dataclass(frozen=True)
class PlannedCandidates:
    baseline: PlannedQuery
    alternatives: tuple[PlannedQuery, ...]
```

Each plan must have:

- a stable plan fingerprint derived from logical/physical structure but not
  query values or secrets;
- a complete root `PlanProperties` object;
- no unresolved logical field references;
- no node without an executor implementation;
- no remote node without a compiler/capability provider for its source kind.

## Physical plan model

The output is a directed acyclic graph. A tree is sufficient for V0.1 baseline
assembly, but modeling dependencies explicitly now avoids a later redesign for
key transfer and parallel execution.

### Node types to implement now

```text
RemoteScan
  source-local request: approved resource, physical projection, pushed filter,
  optional local order/limit, identity field.

RecordAssembly
  anchor RemoteScan + contributor RemoteScans
  → left-enrich anchored records using declared logical IDs.

CoordinatorFilter
  SQL-like three-valued evaluation of the full original Boolean expression
  over assembled logical records.

CoordinatorSortPage
  deterministic global effective order and keyset-page preparation.

ResultProject
  removes fields pulled only for identity/filter/order work and returns the
  caller's requested public fields plus logical id.
```

The baseline multi-source pipeline is deliberately explicit:

```text
RemoteScan(crm: id, name, status; pushed status = 'active')
                 │
                 ├───────────┐
                 ▼           │
           RecordAssembly ◄──┘ RemoteScan(billing: id, plan)
                 │
                 ▼
       CoordinatorFilter(full original expression)
                 │
                 ▼
       CoordinatorSortPage(effective logical order, page)
                 │
                 ▼
             ResultProject(id, name, plan)
```

`CoordinatorFilter` is emitted only when a source did not enforce the whole
filter. It is omitted when (a) one source accepted the entire expression, or
(b) the expression is a pure conjunction whose every leaf was accepted by its
owning source; a contributor leaf is also a required match, so assembly drops
anchor rows that fail it. Anything else (an `OR`/`NOT` across sources, an
operator the source refuses such as `contains`, or a contributor `IS NULL`)
keeps the full original expression at the coordinator. The source then owns
the semantics of every filter it accepted, so adapters must be verified with
real-database tests; this replaces an earlier "always re-check" rule.

### Node types reserved for the next planner increment

```text
KeySet
  materialize and deduplicate a bounded logical-id stream.

RemoteKeyLookup
  source-local lookup using a KeySet in bounded parameter batches.

NativeRelation
  one source adapter executes a declared relationship internally.

Traverse
  bounded declared graph/relationship path. It is never an arbitrary edge scan.

SemanticCandidateSearch
  produces a bounded candidate ID set with exact/approximate metadata.

Materialize
  explicit barrier only when downstream work truly needs all input rows.
```

Do not add these plan node classes without corresponding compiler/executor
contracts and tests. A named class alone is not a feature.

## Plan properties: the invariants every node must declare

The most important missing structure in the current prototype is a formal
property contract. The planner compares or connects nodes only when their
properties match.

```python
@dataclass(frozen=True)
class PlanProperties:
    output_fields: tuple[BoundField, ...]
    logical_id: BoundField | None
    ids_are_unique: bool
    ordering: tuple[BoundOrderTerm, ...] | None
    location: PlanLocation              # source alias or coordinator
    completeness: ResultCompleteness    # exact / approximate / unknown
    result_shape: ResultShape           # record / id_set / edge_set later
    catalog_fingerprint: str
```

### Required invariants

1. **Every remote scan projects its source representation's logical ID.**
   Identity is required for assembly, key transfer, deterministic tie-breaking,
   provenance, and result shaping—even if the caller did not request `id`.
2. **Only source-owned mapped fields appear in a remote projection/filter.**
3. **Every remote predicate is either fully supported by that adapter or is
   left in the coordinator residual.**
4. **A `RecordAssembly` has exactly one anchor and contributors whose IDs are
   unique according to active catalog validation.**
5. **Assembly is left-enrichment for a root dataset in V0.1.** Contributor-only
   IDs do not create records; absent contributor fields become `null`.
6. **A global ordering exists only after all order fields are available at the
   coordinator, unless one source alone proves it owns the complete result.**
7. **A source-local `LIMIT`/Top-N is pushed only when it cannot discard a
   globally valid result.**
8. **Every plan preserves the exact catalog fingerprint against which it was
   bound.**

## Adapter capability and compiler contracts

The planner must ask adapters about semantic capability in a structured way.
“PostgreSQL supports filters” is too broad: each adapter must approve the
specific requested fragment.

```python
@dataclass(frozen=True)
class PushdownDecision:
    accepted_filter: BoundFilterExpression | None
    residual_filter: BoundFilterExpression | None
    accepted_projection: tuple[ResolvedField, ...]
    accepted_order: tuple[BoundOrderTerm, ...]
    accepted_limit: int | None
    limit_is_guaranteed: bool
    reasons: tuple[str, ...]


class SourcePlanningAdapter(Protocol):
    source_kind: SourceKind

    def plan_remote_scan(
        self,
        source: SingleSourceQueryBinding,
        requested: SourceOperationRequest,
        active: CatalogEvaluation,
    ) -> PushdownDecision: ...


class SourceFragmentCompiler(Protocol):
    source_kind: SourceKind

    def compile_scan(self, scan: RemoteScan) -> CompiledRemoteOperation: ...
```

### Why one specific decision instead of boolean capabilities

A static `supports_filter=True` flag is insufficient. It cannot say:

- a PostgreSQL adapter accepts `eq`, `in`, `is_null`, and a specific compound
  conjunction, but not a text operator currently missing portable semantics;
- a graph adapter accepts one bounded relationship edge but not a two-hop path;
- a vector adapter accepts a semantic top-k request but cannot guarantee exact
  result ordering;
- a source accepts an order but cannot guarantee applying the requested limit.

The adapter returns what it accepted and what remains. The planner makes that
decision visible in the physical plan and retains safe coordinator fallback.

### PostgreSQL V0.1 implementation

The PostgreSQL planning adapter initially accepts:

- source-owned projection fields plus mandatory logical ID;
- `eq`, `ne`, `in`, `not_in`, null tests, and numeric/timestamp ranges;
- arbitrary Boolean expressions **only when every referenced field belongs to
  this same source and the compiler supports every leaf**;
- local order/limit only for complete single-source queries.

It initially refuses pushdown of:

- `contains` and `starts_with` until the project defines portable collation and
  case semantics;
- any expression containing fields from another source;
- global multi-source ordering/page limits;
- semantic/traversal expressions;
- caller-provided SQL functions or raw native syntax.

The PostgreSQL compiler must compile `RemoteScan`, not `SourceResolvedQuery`.
That changes the concrete boundary from:

```text
resolved query → one single-source SQL statement
```

to:

```text
RemoteScan(source alias, approved physical fields, accepted filter) → SQL
```

This is the change that makes actual federated pushdown testable.

## Semantic rewrite rules

Rules are deterministic and ordered. They do not use statistics or cost.

### Rule 0 — root requirements

Construct a `RequiredFields` set from:

- caller projection;
- every field in the complete filter expression;
- every global order term;
- the mandatory root logical ID;
- fields required by a later declared relationship/traversal (future).

This prevents the current bug class where a contributor scan omits its logical
ID because the caller did not explicitly select it.

### Rule 1 — source fragment partitioning

Partition required fields by their approved `SourceResolvedQuery` ownership.
For every participating source, construct a source fragment that includes:

- its mandatory source logical-ID mapping;
- every source-owned required field;
- no unmapped or foreign-source field.

No physical name matching, inferred joins, or foreign-key discovery changes
this partition. YAML mappings and the active catalog are authoritative.

### Rule 2 — projection pushdown

Request only required source-owned fields from each remote scan. The source ID
is added whether or not it appears in caller projection.

Projection is a mandatory optimization when the adapter accepts it because it
cannot change record values for requested fields. If a source cannot project,
it must return a defined complete-row envelope which is trimmed at the
coordinator; V0.1 PostgreSQL must support projection.

### Rule 3 — whole-expression same-source pushdown

If the complete Boolean expression references fields from exactly one source
and that adapter accepts it, push the whole expression into that source scan.
When the source accepts it, no coordinator filter is emitted.

### Rule 4 — conjunctive source-local pushdown

For a top-level `all` tree, flatten its leaves. Push each leaf into its owning
source only if that adapter accepts it. Leave the full original expression as
the coordinator residual.

Example:

```yaml
where:
  all:
    - {field: status, op: eq, value: active}       # CRM
    - {field: plan, op: eq, value: enterprise}     # Billing
```

Becomes:

```text
CRM RemoteScan:     WHERE account_status = $1
Billing RemoteScan: WHERE subscription_plan = $1
Coordinator:        status = 'active' AND plan = 'enterprise'
```

Both remote predicates reduce source rows, network bytes, and coordinator
work. The coordinator filter is omitted here because both conjuncts were
accepted by their owning sources.

### Rule 5 — do not split `any` or `not` across sources

For an `any` (OR) or `not` spanning sources, push nothing unless a later proof
rule establishes a semantics-preserving transformation under SQL null logic.

Example:

```yaml
where:
  any:
    - {field: status, op: eq, value: active}       # CRM
    - {field: plan, op: eq, value: enterprise}     # Billing
```

The V0.1 baseline retrieves both fragments, assembles records, then evaluates
the full OR at the coordinator. Pushing only one side would lose records.

### Rule 6 — ordering and page placement

- For a complete single-source query, request source order and limit when the
  adapter explicitly guarantees both.
- For a multi-source query, do not push caller page size or global order into
  individual source scans. It can discard records that would appear after
  assembly/filtering.
- Apply the validated effective ordering (including hidden `id ASC`
  tie-breaker) and page at the coordinator.

Later optimization can add an explicitly proven over-fetch/Top-N rule. It is
not a V0.1 shortcut.

### Rule 7 — relationship and graph placement (future hook)

Only a declared relationship may create a multi-dataset edge. If endpoints and
the relationship implementation live in one capable source, an adapter may
propose a `NativeRelation` node. Otherwise the planner emits a bounded
coordinator/key-transfer plan. It never accepts caller-supplied edge labels,
join syntax, table names, or traversal procedures.

## Baseline plan construction algorithm

```text
1. Verify resolved.catalog_fingerprint == active catalog fingerprint.
2. Derive RequiredFields from select/filter/order/id.
3. Build one source fragment per participating source, always including ID.
4. Ask the relevant planning adapter to accept/refuse each fragment operation.
5. Construct RemoteScan nodes from accepted portions.
6. If exactly one source owns all required data:
     RemoteScan → optional CoordinatorFilter → optional CoordinatorSortPage
       → ResultProject
7. If multiple sources participate:
     anchor RemoteScan + contributor RemoteScans
       → RecordAssembly
       → CoordinatorFilter(full original filter)
       → CoordinatorSortPage
       → ResultProject
8. Validate every node's PlanProperties and executor/compiler availability.
9. Create a deterministic plan fingerprint and safe PlanExplanation.
10. Return exactly this baseline plan.
```

At this stage the planner does not look at rows, indexes, costs, or latency.
It guarantees a baseline that runs and preserves meaning.

## Compiler handoff

### New compiled-operation contract

Replace the current compiler input `SourceResolvedQuery` with `RemoteScan`.

```python
@dataclass(frozen=True)
class CompiledRemoteOperation:
    source_kind: SourceKind
    source_name: str
    connection_ref: str
    output_columns: tuple[CompiledOutputColumn, ...]
    native_payload: object             # adapter-owned, parameterized
    plan_fingerprint: str
```

The PostgreSQL implementation contains:

- catalog-derived quoted resource/column identifiers only;
- user values only in bound parameter positions;
- the physical projection mandated by `RemoteScan`;
- exactly the accepted pushed filter expression;
- accepted order/limit only when present on the scan;
- output aliases keyed by logical field names.

The compiler must reject any `RemoteScan` that references a field it does not
own or an operator it did not accept. This is defense in depth, not merely a
planner assertion.

## Baseline executor design

The executor must run the planner output—not reconstruct a plan itself.

```python
class FederatedExecutionEngine:
    def execute(self, query: Mapping[str, object]) -> QueryExecutionResult:
        active = runtime.require_active()
        bound = bind(parse(query), active)
        resolved = resolve(bound, active)
        planned = planner.plan(resolved, active)
        compiled = compiler.compile_all(planned.plan)
        return executor.execute(compiled, planned.plan, active)
```

### V0.1 node execution behavior

| Node | Execution | Guard |
| --- | --- | --- |
| `RemoteScan` | compiler adapter creates command; execution adapter returns logical rows | source row cap + one extra row; source timeout |
| `RecordAssembly` | anchor records form output; contributors enrich only matching IDs | require identity fields; bounded row map/memory |
| `CoordinatorFilter` | existing SQL-like three-valued expression evaluator | no implicit coercion |
| `CoordinatorSortPage` | stable effective order and keyset preparation | reject if candidate materialization exceeds configured bound |
| `ResultProject` | remove internal helper fields; include required logical ID | never expose internal fields |

Baseline multi-source scans run sequentially initially. This makes dependency,
memory, and error handling simple and deterministic. Independent parallelism
is a later scheduler feature, not an assumption built into plan semantics.

### Execution errors

Add typed errors before wiring the engine:

- `QUERY_PLAN_UNSUPPORTED` — no planner/compiler/executor implementation for a
  valid logical query;
- `QUERY_PLAN_INVARIANT_VIOLATION` — internal plan properties are inconsistent;
- `QUERY_ROW_LIMIT_EXCEEDED` — remote scan produced more than its configured
  safe bound;
- `QUERY_COORDINATOR_MEMORY_EXCEEDED` — assembly/sort guard would be exceeded;
- `QUERY_PLAN_CATALOG_MISMATCH` — an old plan is asked to run under another
  catalog;
- existing source timeout/unavailability errors propagate with source alias.

## Explainability

Build `explain()` with the baseline planner before cost estimation. It must not
open a connection or execute remote work.

Example safe explanation:

```yaml
plan_kind: in_memory_record_assembly
catalog_fingerprint: "..."
nodes:
  - kind: remote_scan
    source: crm_postgres
    dataset: customer
    fields: [id, name, status]
    pushed_filter: "status eq <bound-value>"
  - kind: remote_scan
    source: billing_postgres
    dataset: customer
    fields: [id, plan]
    pushed_filter: "plan eq <bound-value>"
  - kind: record_assembly
    anchor: crm_postgres
    contributors: [billing_postgres]
  - kind: coordinator_filter
    reason: "preserve complete Boolean semantics"
  - kind: coordinator_sort_page
    ordering: [id asc]
```

The explanation uses logical field names and source aliases. It redacts query
values, connection references, physical columns, native commands, and source
statistics values by default.

## Candidate expansion after baseline execution exists

The baseline has passed PostgreSQL E2E tests. The next V0.1 planner increment
must make its output `PlannedCandidates` and choose one executable candidate.

This is **required V0.1 scope**, not an optional later optimization. A
federated planner must decide whether it is safer and cheaper to fetch bounded
records from every source or to transfer a bounded set of logical IDs from one
source to another. The caller never chooses this strategy.

The present implementation produces only Candidate A below. It is correct but
can transfer unnecessarily many records. V0.1 is complete only after the
planner can generate Candidates A, B, and C when their adapters and hard
limits allow them, estimate them, select one, execute it, and explain that
choice.

### Required V0.1 candidate-selection flow

```text
validated logical query
  → resolve source ownership and declared logical-ID links
  → generate every semantically valid bounded candidate
      A: independent bounded scans and coordinator assembly
      B: forward logical-ID transfer
      C: reverse logical-ID transfer
  → discard a candidate lacking adapter/compiler/executor support
  → discard a candidate exceeding hard row, ID, byte, or batch limits
  → estimate each remaining candidate
  → select the lowest-cost safe candidate
  → execute the selected physical plan
  → return a redacted explanation of selected and rejected candidates
```

The federated planner owns candidate generation and selection. The cost module
only estimates already-valid candidates; it must not invent a transfer plan.
PostgreSQL, Neo4j, and other source engines still own their internal index and
join choices for each native command YoDb sends them.

### Required V0.1 contracts and limits

Add these contracts under `src/yodb/planning` before implementing transfer:

- `PlannedCandidates`: the candidate set, selected plan, and safe
  selected/rejected explanation;
- `KeySet`: a deduplicated logical-ID stream with ID-count and byte facts;
- `RemoteKeyLookup`: an adapter-approved lookup of a declared logical-ID
  mapping, including lookup field, batches, and residual source filter;
- `TransferPolicy`: maximum IDs, encoded bytes, batches, and records per
  batch; and
- `CandidateRejection`: a redacted reason such as unsupported lookup,
  transfer-size limit, or unavailable estimate.

`PlannerPolicy` proposes the hard bounds while execution independently
enforces them. Limits are server/operator configuration, not query input and
not caller-authored YAML. A source adapter declares whether it can safely do a
logical-ID lookup; PostgreSQL implements it first, while future Neo4j, Mongo,
and vector adapters implement equivalent capability contracts.

### Candidate 1: independent scan scheduling variant

Same physical result as baseline, but marks remote scans as parallel-eligible.
The executor/scheduler must still respect source and pool limits.

### Candidate 2: anchor-to-contributor key transfer

```text
RemoteScan(anchor with pushed source-local filters)
    → KeySet(deduplicate IDs; hard max)
    → RemoteKeyLookup(contributor; bounded batches)
    → RecordAssembly
```

This is valid only when:

- the contributor identity mapping is unique and validated;
- contributor adapter explicitly supports the key lookup;
- key cardinality/bytes/batches have hard plan and runtime bounds;
- the entire result can still be assembled with root anchor semantics.

### Candidate 3: reverse key transfer

Create only when a contributor has a selective pushed filter and the root
source can perform its inverse declared-ID lookup. It is not valid merely
because both fields happen to have similar names.

### Candidate 4: same-source native relation

Create only when a single adapter explicitly confirms it can execute every
source representation and the declared relationship. PostgreSQL chooses its
own native join strategy; YoDb sees one `RemoteRelation` fragment.

### Candidate limits

V0.1 limits should be explicit:

- root dataset count: 1;
- relationship hops: 0 for baseline, later server-configured maximum;
- source representations: server-configured maximum, recommended 3;
- transfer directions per direct contributor: at most 2;
- native-relation candidate: at most 1 per relationship implementation;
- planning candidates: server-configured cap, recommended 8;
- every partial candidate pruned if it lacks compiler/executor support.

At that point the cost module can compare candidates. It must never manufacture
a key-transfer candidate on its own.

## Implementation milestones

### Milestone P0 — reset the planning boundary

**Goal:** establish the correct contracts before behavior changes.

1. Replace/adapt the current planning prototype to use the node model and
   `PlanProperties` in this document.
2. Remove the assumption that a `SourceScanPlan` projection is merely
   `source.fields`; make mandatory source logical ID an invariant.
3. Replace static broad capability flags with a per-fragment
   `PushdownDecision` contract.
4. Make cost package imports depend on planner output only after this contract
   stabilizes. Do not use cost selection from `QueryExecutionEngine`.
5. Add planning-specific error codes and a plan fingerprint.

**Tests:** construct a bound/resolved query with no database, assert exact
node structure/properties/explain output for one source and two sources.

### Milestone P1 — PostgreSQL remote fragment compilation

**Goal:** make pushdown concrete SQL rather than planner annotation.

1. Introduce `CompiledRemoteOperation` and `compile_scan(RemoteScan)`.
2. Refactor the existing PostgreSQL compiler's secure identifier/value logic
   into the new remote-scan compiler.
3. Preserve the legacy single-source engine during the refactor until the new
   plan path has equivalent result tests.
4. Add a compiler assertion that logical ID is projected for every scan.

**Tests:** exact parameterized SQL assertions for projection, one predicate,
multiple `all` predicates, `in`, null tests, ranges, full same-source OR/NOT,
and refused text predicates. Verify no cross-source field appears in a remote
SQL command.

### Milestone P2 — baseline physical executor

**Goal:** make the planner's baseline DAG the sole execution path.

1. Implement `RemoteScan`, `RecordAssembly`, `CoordinatorFilter`,
   `CoordinatorSortPage`, and `ResultProject` executors.
2. Refactor `QueryExecutionEngine` to parse/bind/resolve/plan/compile/execute.
3. Retire the direct `SourceResolvedQuery → compiler` execution path after
   compatibility tests pass.
4. Enforce source row cap, coordinator assembly cap, and plan/catalog
   fingerprint check.

**Tests:** execute real PostgreSQL scans and compare baseline multi-source
results to a known native SQL join only in the test harness. The production
path remains source-authoritative and never accepts raw SQL.

### Milestone P3 — pushdown verification matrix

**Goal:** prove actual remote operations, not just plan annotations.

Use a PostgreSQL container with deliberately skewed data and independently
mapped CRM/Billing representations. Capture compiled parameterized SQL and
returned row counts for each source:

| Case | Expected remote behavior | Expected coordinator behavior |
| --- | --- | --- |
| one-source equality | one pushed predicate | defensive residual, same results |
| one-source `all` | all supported leaves pushed | same results |
| one-source `any`/`not` | whole expression pushed if compiler supports it | same results |
| source-local `in` | membership pushed with values bound | same results |
| source-local null test | null predicate pushed | same results |
| source-local range | range pushed | same results |
| CRM AND Billing predicates | each source receives its own leaf | complete AND rerun after assembly |
| CRM OR Billing predicate | neither fragment receives partial OR | full OR after assembly |
| filter only in contributor | contributor filter pushed | anchor remains root/left-enrichment |
| order/page over multiple sources | no per-source page truncation | global sort/page after assembly |
| unsupported text operator | no unsafe SQL | typed unsupported/planning error |
| internal/unmapped field | no plan constructed | existing query error |

For each case assert:

- the physical plan/explain node structure;
- exact source SQL shape and bound parameter values in a test-only capture;
- source rows read are reduced when a filter is pushed;
- final logical rows equal expected results;
- no source receives another source's physical field;
- user-visible response never includes helper/internal fields.

### Milestone P4 — baseline operational behavior

**Goal:** turn a correct plan into a safe service behavior.

1. Add source timeout propagation and cleanup tests.
2. Add “one extra row” scan-bound detection.
3. Add coordinator assembly and global-sort memory/row guards.
4. Add deterministic error mapping and cancellation boundary.
5. Add non-executing explain endpoint/API.

### Milestone P5 — cost model integration

**Goal:** make the cost module useful only now that plans run.

1. Feed complete baseline `ExecutablePlan` into the cost estimator.
2. Use actual `PlanProperties` and adapter capability decisions, not inferred
   field/source guesses.
3. Implement alternative candidate templates: key transfer, reverse transfer,
   native same-source relation, and parallel eligible scans.
4. Have cost policy choose only among candidates for which compilation and
   execution tests already exist.
5. Add estimate-versus-actual telemetry with no business values or native query
   text in ordinary logs.

## Definition of done for the planner baseline

The planner baseline is complete only when all statements below are true:

1. `QueryExecutionEngine` always asks the planner for a physical plan.
2. Every remote scan in that plan is compiled from `RemoteScan`, never from a
   whole resolved query.
3. The PostgreSQL container tests show the exact pushed SQL for each source in
   a multi-source conjunction.
4. The same tests prove partial cross-source `OR`/`NOT` is not pushed.
5. Every remote scan contains the mapped logical ID and only allowed mapped
   fields.
6. Multi-source assembly, residual filtering, global ordering/page, and final
   projection run through the planner's DAG and return expected logical rows.
7. Resource bounds fail deterministically rather than silently truncate.
8. `explain()` shows source aliases, logical fields, pushed/residual operations,
   and plan properties without executing a query.
9. No cost model affects execution selection yet.

Only after this definition of done may we call the cost model an optimizer
integration rather than a detached estimator.
