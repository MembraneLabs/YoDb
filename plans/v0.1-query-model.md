# V0.1 Query Model

**Status:** the initial relational core is implemented in `src/yodb/query`.
Traversal and semantic search remain planned extensions. This document
describes the public, logical query model. It deliberately does not prescribe
SQL, Cypher, pgvector index choice, source names, physical table names, or an
execution strategy.

## Why this exists

YoDb's query boundary is the important abstraction boundary:

```text
application / agent
        |
        | structured logical query
        v
  validate against active catalog
        |
        | bound logical query
        v
  planner and source-specific compilers
        |
        v
 PostgreSQL / Neo4j / future adapters
```

The caller says *which business dataset and fields it wants*. YoDb determines
how those fields are mapped to approved read-only sources and how the work is
executed. A PostgreSQL compiler might produce SQL today; a Neo4j compiler or a
different relational adapter can consume the same bound query later.

This is not a natural-language interface and is not raw SQL. An MCP or agent
layer may help a user discover datasets and construct this object, but it must
submit the same structured query to YoDb.

## Non-negotiable rules

- Queries name logical datasets, logical fields, and declared relationships
  only.
- Queries cannot name a database, source, table, column, label, edge type,
  index, embedding model, SQL, Cypher, or source-specific function.
- Every field reference is checked against the currently active catalog.
  Unmapped, unknown, and `visibility: internal` fields are inaccessible.
- An index changes the eventual physical plan, never what a caller is allowed
  to ask. A supported logical field may be filtered or sorted even when no
  suitable index exists, subject to query budgets.
- All values are bound data, never interpolated query text.
- The public model is declarative. It says what result is wanted, not scan
  order, join order, parallelism, or an implementation algorithm.
- A valid query produces the same logical meaning regardless of the adapter
  chosen to execute it. A source that cannot preserve the required semantics
  is not an eligible plan.

## Two representations, one meaning

There are two forms of a query.

1. **Submitted query:** a JSON-serializable object used by a Python SDK, HTTP
   API, or MCP tool. It contains logical names supplied by the caller.
2. **Bound query:** an immutable internal object produced only after
   validation. Its dataset, field, and relationship references point to the
   matching objects in an active `CatalogEvaluation`. It also carries the
   catalog fingerprint used for validation.

The planner accepts only a bound query. This means a catalog refresh cannot
silently reinterpret a query that was validated against an older catalog.

The equivalent internal algebra is intentionally small:

```text
Scan(dataset)
  -> Filter(expression)
  -> Traverse(path)       # optional and bounded
  -> Project(fields)
  -> Order(terms)
  -> Limit / Page

SemanticSearch(...)       # optional candidate-producing operator
Aggregate(...)            # later
Window(...)               # later
```

This is a logical operator tree, not an execution graph. The planner later
turns it into a physical DAG with source scans, key transfers, joins, and
in-memory operations where necessary.

## Submitted query shape

The initial public shape is intentionally compact:

```yaml
from:
  dataset: customer
  as: customer                 # optional; defaults to the dataset name

select:                         # optional; defaults to all public fields
  - id
  - name

where:                          # optional Boolean expression
  all:
    - field: name
      op: starts_with
      value: Acme
    - field: status
      op: eq
      value: active

order_by:                       # optional; deterministic `id ASC` fallback
  - field: name
    direction: asc

page:                           # optional keyset page request
  first: 25
  after: opaque_cursor

constraints:                    # optional; restricted by server policy
  maximum_results: 25
  maximum_latency_ms: 1000
  allow_partial_results: false
```

`from.dataset`, `select`, `where`, and `order_by` are all logical names. The
example does **not** reveal whether `customer.name` is `public.accounts.company_name`
in PostgreSQL, a Neo4j property, or supplied by some later adapter.

For the first useful relational path, `from` contains one dataset. Multi-hop
relationships and semantic search extend this shape without changing the root
query contract.

## Fields, values, and filtering

### Field references

A simple field reference such as `name` is relative to `from.dataset`. A
future multi-dataset query uses the stable qualified form:

```yaml
field:
  scope: ticket
  name: created_at
```

The first implementation may accept the simple form only, but the internal
model should store every reference as a `(scope, field)` pair. This avoids a
breaking redesign when traversal introduces more than one dataset.

`id` is a public, system-level logical field. A source may contribute public
record fields only when it can map that dataset's logical `id`; a source that
only supplies an internal key may still implement an approved relationship.
This keeps record assembly and cross-source transfer anchored on a stable
identity.

### Type handling

The catalog's declared logical type controls validation. Transport values are
decoded once into typed values when the submitted query becomes a bound query:

| Logical type | Accepted query value |
| --- | --- |
| `id` | valid YoDb logical-ID string |
| `string`, `text` | JSON string |
| `int` | JSON integer, not a float |
| `float` | JSON number |
| `bool` | JSON boolean |
| `timestamp` | RFC 3339 timestamp with an explicit UTC offset; normalized to UTC |
| `uuid` | canonical UUID string |
| `json`, `bytes` | not filterable, orderable, or semantically searchable in the initial model |

The validator does not guess or silently coerce incompatible values. For
example, `"12"` is not an `int`, and `"true"` is not a `bool`. This is both
more predictable for callers and avoids adapter-specific coercion differences.

### Boolean expression tree

`where` is one of these nodes:

```yaml
# A leaf predicate
field: status
op: eq
value: active

# Conjunction
all: [<expression>, <expression>]

# Disjunction
any: [<expression>, <expression>]

# Negation
not: <expression>
```

An `all` or `any` expression must contain at least one child. A leaf has
exactly one field and operator. It cannot combine two logical fields; a join is
represented only by a declared relationship traversal.

### Initial predicate operators

| Logical types | Operators |
| --- | --- |
| `id`, `uuid`, `string`, `text`, `int`, `float`, `bool`, `timestamp` | `eq`, `ne`, `in`, `not_in`, `is_null`, `is_not_null` |
| `int`, `float`, `timestamp` | `gt`, `gte`, `lt`, `lte` |
| `string`, `text` | `contains`, `starts_with` |

`in` and `not_in` require a non-empty, bounded array whose elements have the
field's type. `is_null` and `is_not_null` take no value; `eq: null` and
`ne: null` are invalid rather than inheriting an adapter's three-valued-null
quirks. `contains` and `starts_with` are logical text predicates; their exact
case/collation policy must be made explicit before execution (recommended V0.1
policy: Unicode case-sensitive semantics, with PostgreSQL compilation chosen
to preserve that behavior).

The initial model intentionally excludes regex, arbitrary JSON path predicates,
database functions, and raw full-text syntax. They can be added as explicit,
portable operators later instead of leaking one backend's syntax into every
adapter.

## Projection, ordering, and pagination

### Projection

`select` lists public fields from the root dataset. It may not contain
duplicates, internal fields, or unknown fields. If omitted, YoDb returns all
public root fields. The response always includes the logical `id`, even when
the caller does not list it, since it is essential for stable pagination,
provenance, and later relationship results.

### Ordering

Each order term has a public scalar field and `asc` or `desc`. The validator
rejects types that do not have a portable total ordering in V0.1 (`json` and
`bytes`) and rejects an ordering the participating sources cannot preserve.

YoDb appends `id ASC` as a final hidden tie-breaker unless it is already the
last term. With no `order_by`, effective order is `id ASC`. This gives a stable
order even though a physical plan might use different sources or a different
index.

### Pages

V0.1 uses keyset pagination, not offsets:

```yaml
page:
  first: 25
  after: opaque_cursor
```

`first` has a server-configured default and maximum. `after` is an opaque,
signed cursor that binds the catalog fingerprint, normalized query fingerprint,
effective ordering, final sort tuple, final logical ID, and expiry. A cursor
may not be reused with another query or incompatible catalog snapshot.

Pagination is not a global source snapshot: a mutable source can change
between pages. The response must eventually surface its catalog version and
per-source read timestamps so callers can understand this freshness boundary.

## Relationship traversal

Relationships are named logical capabilities declared in `relations.yaml`.
They are not caller-authored joins.

The future traversal extension is shaped like this:

```yaml
traverse:
  - relationship: customer_has_ticket
    direction: forward          # from customer to support_ticket
    as: ticket
    where:
      field: status             # relative to `ticket`
      op: eq
      value: open
```

`forward` always means the declared `from` → `to` direction. `reverse` is
allowed only when the relationship has `direction: bi`. A traversal must:

- begin at the previous path dataset;
- reference a declared relationship with a compatible endpoint and direction;
- carry a bounded number of hops (a server maximum applies even if the caller
  requests fewer);
- use only public fields for its filters and output;
- fit a configured result, transfer, and traversal-work budget.

The planner may implement the same traversal as PostgreSQL joins, a PostgreSQL
edge-table query, a Neo4j traversal, or a controlled cross-source key transfer.
That remains invisible to the caller.

The exact result shape for one-to-many traversal—nested records versus a flat
row/edge envelope—should be decided before traversal implementation. It does
not block the single-dataset query model.

## Semantic search

Semantic search is a logical candidate-producing operator. The caller names a
logical field and describes what it seeks; it never names pgvector or an index:

```yaml
semantic:
  field: content
  query: tickets at risk of churn because of price
  candidates: 100
  verify: false
```

Validation requires the field to be public and `semantic_eligible: true` in the
catalog. A planner may use pgvector today, a bounded exact similarity scan when
permitted by policy, or a future vector adapter. It may intersect semantic
candidates with `where` either before or after retrieval only when that
preserves declared semantics.

Semantic ranking, score semantics, verification, index freshness, and semantic
session cursors need their own final contract before this operator is built.
They are intentionally not part of the first relational implementation.

## Constraints and safety budgets

Constraints express caller needs, while the server remains the authority on
allowed work:

```yaml
constraints:
  maximum_results: 25
  maximum_latency_ms: 1000
  maximum_cost: 1000            # normalized units; only after cost policy exists
  minimum_quality: 0.8           # semantic queries only; later
  allow_partial_results: false
```

The validator rejects non-positive values, unknown constraint fields, and
requests beyond configured limits. `allow_partial_results` should have no
effect on a single-source relational query; it becomes meaningful only for
federated plans and must never conceal missing data. Any partial result needs
explicit warnings and source provenance.

## What is intentionally later

The following are not accepted by the initial query model implementation:

- raw SQL, Cypher, CTE text, database functions, or physical identifiers;
- user-authored joins or arbitrary field-to-field comparisons;
- aggregates, `GROUP BY`, `HAVING`, windows, set operations, subqueries, and
  arbitrary expressions;
- offset pagination;
- unbounded graph paths or unrestricted recursive queries;
- source/index/model selection;
- mutations and distributed transactions.

CTEs and window functions may be generated internally by a future PostgreSQL
compiler from explicit typed operations. They are not public escape hatches.

## Validation result and errors

Validation runs against `InMemoryCatalogRuntime.require_active()` and contacts
no data source. Success returns a `BoundQuery` plus a deterministic fingerprint
of its canonical normalized representation. Failure returns one structured
error with a safe location and code, for example:

| Condition | Example code |
| --- | --- |
| no active catalog | `catalog_runtime_uninitialized` |
| dataset does not exist | `dataset_not_found` |
| field is missing or internal | `field_not_accessible` |
| value is incompatible | `query_value_type_invalid` |
| operator/type combination is invalid | `query_operator_not_supported` |
| invalid Boolean expression | `query_expression_invalid` |
| unsafe limit/cursor | `query_limit_invalid`, `cursor_query_mismatch` |
| undeclared/invalid traversal | `relationship_not_found`, `traversal_not_allowed` |

Errors must identify logical locations such as `where.all[1].value`, never a
physical table, SQL fragment, connection string, or database credential.

## Implementation sequence

1. Define frozen Python request/IR models, expression nodes, type-aware values,
   error codes, and canonical serialization/fingerprints.
2. Implement validation against an active catalog for a single root dataset:
   projection, Boolean filters, ordering, limits, and page request shape.
3. Resolve a bound query into declared single- or multi-source participation
   objects, linked only by each contributor's stable logical `id` mapping.
4. Compile one resolved PostgreSQL source binding into quoted identifiers and
   parameterized SQL, without executing it.
5. Add exhaustive unit tests that demonstrate rejected unknown/internal fields,
   bad types, unsafe values, and raw/physical identifiers.
6. Add declared bounded traversal validation and then its result envelope.
7. Add semantic-query validation after the semantic contract is finalized.
8. Build the PostgreSQL executor. It receives
   no caller-supplied SQL identifiers or values.
9. Build the initial backend-neutral physical plan model: source scan,
   single-source plan, and in-memory logical-ID record assembly. For the
   first federated implementation, scan each participating source under a
   hard row budget, assemble anchored records in YoDb memory, then apply the
   full Boolean filter, global ordering, and page only after assembly.

## Deferred physical-plan optimization notes

The initial multi-source plan is deliberately a correctness baseline, not an
optimizer. It must not silently drop rows by applying a caller page limit to
each source, and it must not push an arbitrary cross-source Boolean expression
into one source. The following work is explicitly deferred:

1. **Parallel scan scheduling:** execute independent source scans concurrently
   while preserving bounded connection-pool use and deterministic errors.
2. **Safe predicate pushdown:** push only predicates proven source-local and
   semantics-preserving; start with conjunctive leaves. Cross-source `any` and
   `not` expressions require more careful algebra.
3. **Same-source join pushdown:** when both representations are compatible and
   colocated in PostgreSQL, compile a native join rather than transferring
   rows through YoDb memory.
4. **Cost and budget planning:** use inspection metadata, statistics, index
   facts, cardinality estimates, source latency, transfer bytes, and memory
   estimates to reject or choose among plans before execution.
5. **Graph and semantic nodes:** add declared relationship traversal and
   semantic candidate stages only after their result and freshness contracts
   are finalized.

## Decisions still needed before implementation

The core model is ready to implement once these focused policies are confirmed:

1. **Text semantics:** case-sensitive (recommended) or case-insensitive;
   accent behavior and locale/collation policy.
2. **Default and maximum page size:** recommendation: default 100, maximum
   500, with a lower server policy allowed per deployment.
3. **Root record source rule:** approve the `logical id required for public
   field contribution` rule above, or define a deterministic alternative.
4. **Traversal response shape:** nested records/edges or flat rows when a
   one-to-many relationship is traversed.
5. **Semantic contract:** score interpretation, verification mode, candidate
   limits, and freshness/session cursor policy.
