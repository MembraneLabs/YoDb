# Operators: One Vocabulary, One Structure

Every kind of work a query can need is an **operator**. All layers read the same
catalog (`yodb.operators.OPERATORS`), so there is one answer to "what operators
exist, which are implemented, and how can each run".

```
 query ──► terms (registered)            "semantic: {...}" is a term; plain predicates are built in
   │
   ▼
 PLANNER = fixed relational spine  +  extension operators (plug in after filtering)
   │         scan → combine → filter → [extensions] → order/page → project
   │         each operator lists its legal STRATEGIES; the optimizer picks among cost VARIANTS
   ▼
 PLAN of nodes ── each node names its operator, describes itself, rewrites itself
   │
   ▼
 EXECUTOR = one HANDLER per node type, found in a registry

 ADAPTERS declare, per source, which operators/abilities the database runs itself.
```

## The catalog

| Operator | Category | Status | Strategies |
| --- | --- | --- | --- |
| `scan` | relational | implemented | plain |
| `filter` | relational | implemented | push_to_source, run_in_yodb |
| `project` | relational | implemented | push_columns |
| `order` | relational | implemented | push_to_source, run_in_yodb |
| `limit` | relational (needs `order`) | implemented | push_to_source, run_in_yodb |
| `combine` | relational | implemented | read_order, restrict_by_ids |
| `key_lookup` | support | implemented | in_list |
| `vector_search` | support | implemented | ranked_read |
| `semantic_filter` | extension | implemented | verify_all, vector_shortlist |
| `join` | relational | planned | cross-dataset join over a declared relationship |
| `aggregate`, `group_by` | relational | planned | count/sum/avg/min/max; per-group |
| `distinct`, `union` | relational | planned | |
| `traverse` | extension | planned | bounded graph hops |

*Combine* is the same-dataset case: one logical record assembled from several
sources by logical ID. *Join* is the cross-dataset relational join and is not
the same thing. Planned operators are in the catalog so adapters and plans can be
designed against them; nothing can run them yet and an adapter reports them as
`unavailable`.

## Where each operator lives

| Operator | Query | Planning operator | Plan node | Execution handler |
| --- | --- | --- | --- | --- |
| scan (+ pushdown) | built in | `planning/operators/scan.py` | `RemoteScan` | `execution/operators/scan.py` |
| combine | built in | `…/combine.py` (+ cost search) | `RecordAssembly` | `…/combine.py` |
| filter | predicates | `…/filter.py` | `CoordinatorFilter` | `…/filter.py` |
| order, limit | `order_by`, `page` | `…/order_page.py` | `CoordinatorSortPage` | `…/order_page.py` |
| project | `select` | `…/project.py` | `ResultProject` | `…/project.py` |
| semantic filter | `query/semantic.py` (term) | `semantic/planning.py` | `SemanticVerify` | `semantic/execution.py` |

The semantic filter is a plug-in. Everything about it (planning, its node, its cost
settings, execution, its report) lives in `src/yodb/semantic/`, and
`SemanticExtension` is the only thing the engine is given (see below). The core
packages (`query`, `planning`, `execution`) do not import it; `tests/test_boundaries.py`
fails if they ever do.

Shared pieces: `planning/optimizer.py` (generic over *variants*), `planning/contracts.py`
(`PhysicalNode`: operator kind, `inputs`, `with_inputs`, `shape`, `describe`),
`execution/operators/base.py` (`ExecutionContext`, `Run`, handler registry),
`query/extensions.py` (`TermExtension`, `TermRegistry`).

## What an adapter shows

`operator_support(capabilities)` / `describe_capabilities(capabilities)` derive, from
the same declaration the planner reads, how each operator can run against that
source: `source` (the database runs it), `coordinator` (YoDb runs it, possibly
using the source's abilities) or `unavailable`, with the strategies that makes
legal. A source without vector search simply lacks the `vector_shortlist`
strategy; one without key lookup lacks `restrict_by_ids`.

## Strategies and variants

A *strategy* is one legal way to run an extension operator on this query (e.g.
semantic: `verify_all`, `shortlist:200`). It carries a *variant* (what the cost
model sees: a cost function, an optional demand on how the anchor is read, whether
it is approximate), plus how it changes the scans and how it builds its node.
The optimizer knows nothing about any operator: it reads the order sources are
read in and picks the cheapest feasible variant. The fixed rules are always
available as the default.

## Plugging an extension in

An extension is one object with two halves, passed to the engine:

```python
extension = SemanticExtension(SemanticRuntime(verifier, embedder))   # policy and costs derive from the providers
engine = QueryExecutionEngine(catalog, compilers, executors, extensions=[extension])
result = engine.execute(query)
result.reports["semantic"]        # what it did; each extension reports under its own name
```

* `planning_operator(services)` gives the planner its operator (claim, strategies);
* `handlers()` gives the executor a handler per node type it adds.

Its own settings stay with it: `SemanticPolicy` (limits and rules), `SemanticCosts`
(what verification and ranking cost, recall model). The generic cost parameters
(`CostParameters`) hold only what every extension shares. Per-deployment query
limits for a term go in `QueryValidationPolicy(limits={"semantic": 2})`.

## Adding an operator

Everything below is additive; the planner, optimizer and executor do not change.

1. **Catalog**: add the `OperatorKind` and `OperatorSpec` (or flip `planned` to `implemented`).
2. **Plan node**: a dataclass deriving `PhysicalNode` (or `UnaryNode`) that implements
   `shape()` and `describe()`; explain, fingerprint and rewrites then work.
3. **Execution handler**: `handler(context, node, run) -> rows`, returned from the
   extension's `handlers()` (or passed to `FederatedPlanExecutor(handlers=...)` in a test).
4. **Planning operator** (for an extension): `claim(where)` the terms it owns and
   `plan(...)` returning an `ExtensionPlan` of `Strategy` objects with a default;
   expose it as `planning_operator(services)` on the extension.
5. **Query term** (if it is a new filter term): a `TermExtension` (parse, bind,
   describe, fields it reads, placement rules) in a `TermRegistry`.
6. **Adapter capability** (if a source can run it): a field on `SourceCapabilities`
   and a `@support_view(OperatorKind.X)` function next to the operator (no central
   list to edit).

`tests/test_planning_operators.py` and `tests/test_query_extensions.py` do exactly
this with a toy extension (`tests/support/toys.py`), end to end, as the proof.

## Limits (honest)

* One extension operator per query is costed by the optimizer; with several, the
  fixed rules plan them (and the explanation says so).
* The relational spine is fixed. `aggregate`, `group_by`, `distinct`, `union` and
  `join` will each need their own slot in it; they are catalogued, not built.
* `traverse` is a query *clause*, not a filter term; the clause-level registry it
  needs does not exist yet.
* Execution supports one semantic condition per query even if the validator limit is
  raised: a second term is refused, never silently dropped.
