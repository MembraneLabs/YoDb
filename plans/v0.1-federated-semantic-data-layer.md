# V0.1 — Federated Semantic Data Layer

## Status and authority

This is the controlling V0.1 delivery plan. It combines the original logical
data-layer architecture with the focused semantic-runtime thesis:

> YoDb gives applications and agents one typed, explainable way to run
> relational, semantic, and bounded graph queries across connected data sources
> without requiring a data migration.

It supersedes conflicting V0 scope in
[v0-semantic-runtime.md](v0-semantic-runtime.md) and
[ai-data-layer-roadmap.md](ai-data-layer-roadmap.md). The long-term plans remain
architecture references; they do not expand V0.1 scope.

## Product boundary

V0.1 is a read-only query layer, not a replacement database. A team connects
existing sources using least-privilege credentials; YoDb introspects schema,
maintains logical metadata, plans a query, executes source-specific reads, and
returns normalized results plus an explanation.

```text
Applications / agents / Python SDK
                |
                v
         Typed logical query IR
                |
                v
      validator + planner + explain
                |
      +---------+----------+
      |                    |
      v                    v
PostgreSQL + pgvector    Neo4j (optional graph source)
 relational + semantic      graph traversal
 graph edge tables
```

The initial supported capability-to-implementation mapping is deliberately
small:

| Logical capability | V0.1 implementation |
| --- | --- |
| Relational scan/filter/project/order/limit | PostgreSQL |
| Semantic candidate retrieval | pgvector in PostgreSQL |
| Semantic proposition verification | Configured model/classifier provider |
| Graph traversal | PostgreSQL edge tables or Neo4j |
| Cross-capability hydration/filtering | PostgreSQL by logical ID or declared join key |

Neo4j is optional: a deployment can use PostgreSQL edge tables exclusively.
If configured, Neo4j is a graph execution target—not a canonical replacement
and not an application-facing query dialect.

## V0.1 thesis

V0.1 proves two related claims:

1. Teams can remove custom relational/vector/graph query plumbing without
   migrating their data.
2. A semantic predicate can be executed more cheaply and observably than the
   naive `SQL filter -> model evaluation over every candidate` pipeline.

The product is not a generic natural-language-to-database system. Natural
language may be translated by an SDK or agent client, but the runtime executes
only a validated typed query IR.

## Logical model and source metadata

YoDb does not own source data in V0.1. It owns metadata describing how logical
datasets map to connected source schemas.

```text
LogicalDataset
    name, fields, stable logical ID or declared join key
    canonical source preference
    semantic-eligible text fields
    relationship definitions

SourceBinding
    source connection
    table / label / edge mapping
    field mapping
    read freshness metadata

JoinBinding
    left logical field <-> right logical field
    cardinality and source of truth
```

Schema introspection bootstraps this metadata from PostgreSQL and Neo4j.
Humans then review/add annotations for business concepts, join keys, source
precedence, and ambiguous names. V0.1 never guesses a cross-source join or
silently invents a source of truth.

The existing `DatasetSpec`, `RelationshipSpec`, typed fields, canonical-ID
contract, and bounded traversal semantics remain useful as the logical model.
For externally managed data, a declared stable source key may temporarily map
to a YoDb logical ID; YoDb must expose that provenance rather than pretending
it owns the source identifier.

## Typed query IR

The public IR is structured and backend-neutral. It begins with:

```text
Scan
Filter
Project
Order
Limit
SemanticFilter
Traverse (bounded multi-hop)
```

`SemanticFilter` is the key semantic operator:

```text
SemanticFilter(
  ticket.text,
  "The customer is seriously considering cancelling primarily because of price"
)
```

It asks whether a proposition is true of a record. A vector query is only a
possible physical candidate-generation step; callers never name pgvector,
index names, embedding models, a Neo4j label, SQL, or Cypher.

The IR supports execution constraints where a caller needs them:

```text
minimum quality
maximum latency
maximum cost
maximum result count
```

V0.1 uses explicit policies and simple heuristics, not a learned optimizer.

## Query patterns V0.1 must support

### Relational query

```text
PostgreSQL Scan -> Filter -> Project -> Order -> Limit
```

### Semantic query with structured filtering

```text
PostgreSQL Filter
      -> pgvector shortlist
      -> model/classifier verification
      -> canonical PostgreSQL hydration
```

### Graph query

```text
PostgreSQL filter or semantic candidate set
      -> bounded Traverse via Postgres edges or Neo4j
      -> PostgreSQL hydration/filtering
```

### Cross-source graph result

```text
PostgreSQL candidate IDs
      -> declared join key
      -> Neo4j bounded traversal
      -> declared join key
      -> PostgreSQL canonical hydration
```

All cross-source joins must use an approved `JoinBinding`. The planner may push
filters down to a source where supported; otherwise it performs bounded
candidate-set filtering in YoDb. It never executes an unbounded client-side
join as an invisible fallback.

## Semantic physical plans

One `SemanticFilter` has at least two executable plans:

```text
Plan A: deterministic PostgreSQL filters -> model/classifier every candidate
Plan B: deterministic PostgreSQL filters -> pgvector shortlist -> model/classifier verify
```

Plan A is the quality/correctness baseline. Plan B is the primary V0.1
optimization. A later materialized semantic property is a valid third plan but
is not required for V0.1.

The planner compares basic estimates for cardinality, model calls, latency,
cost, retrieval recall/quality, source health, and query limits. It selects a
plan that satisfies the caller contract; if none does, it returns a structured
budget/capability error rather than producing a misleading partial answer.

## Graph behavior

Graph traversal is explicit, typed, and bounded.

- A path uses declared relationships only, with a configurable
  `max_traversal_hops` policy (initial default: 3).
- Per-hop edge and target filters use the normal typed filter language.
- Traversal has intermediate node/edge work budgets.
- PostgreSQL edge tables use SQL joins in V0.1; Neo4j uses an adapter that
  compiles the same IR below the logical boundary.
- Returned nodes are deduplicated by logical ID; deleted/unavailable source
  records cannot be resurrected by a stale graph representation.
- Apache AGE may be evaluated as a PostgreSQL graph implementation later, but
  it is not required for V0.1.

## Explain and observability

Every query returns a query ID. `EXPLAIN`/`EXPLAIN AI` exposes:

```text
logical IR
connected sources considered and selected
source-local operations and pushed-down filters
declared join bindings and candidate-set transfers
graph implementation selected (PostgreSQL edge tables or Neo4j)
semantic plans considered and selected
estimated/actual rows, model calls, latency, cost, and quality signals
freshness/source-version warnings and partial-result conditions
```

The explanation names physical sources for debugging, while the normal query
contract remains logical and portable.

Telemetry records source latency, rows scanned/returned, candidate reductions,
graph expansion, model/provider/version, tokens, cost, confidence, and planner
estimates versus actuals.

## Read consistency and source conflict policy

V0.1 has no distributed transaction or global snapshot. Each source query uses
its own read semantics. Results report source freshness/read timestamps and any
partial-source failure.

When bindings describe the same logical value from multiple sources, the
metadata declares source precedence. The configured canonical source wins;
YoDb surfaces disagreement rather than silently merging conflicting values.

## Delivery milestones

### M0 — Contracts and metadata

- Finalize logical `DatasetSpec`, `RelationshipSpec`, `SourceBinding`, and
  `JoinBinding` representations.
- Keep existing validation/error semantics; add read-only external-source
  provenance.
- Implement source registry and read-only credentials/configuration.

### M1 — PostgreSQL relational connector

- Read-only PostgreSQL connection and schema introspection.
- PostgreSQL adapter for `Scan`, `Filter`, `Project`, `Order`, and `Limit`.
- Typed query validation, source binding, normalized results, and `EXPLAIN`.
- Benchmark simple relational workloads.

### M2 — pgvector semantic execution

- Identify semantic-eligible logical fields bound to Postgres text/embedding
  representations.
- Implement `SemanticFilter` Plan A and Plan B.
- Add model-provider interface, cost/latency/quality estimates, telemetry, and
  `EXPLAIN AI`.
- Benchmark naive versus retrieval-assisted semantic verification.

### M3 — graph execution and composition

- PostgreSQL edge-table traversal adapter.
- Neo4j traversal adapter behind the same typed path IR.
- Declared join bindings for Postgres <-> Neo4j candidate transfer.
- Enforce traversal/candidate budgets, source attribution, and partial-source
  error handling.

### M4 — developer/agent integration and hardening

- Python SDK for structured IR.
- Optional structured tool schema for agents; no autonomous agent framework.
- Annotation/review workflow for source concepts and ambiguous mappings.
- Regression corpus, benchmark suite, explain snapshots, and connector health
  checks.

## Explicit non-goals

```text
source-data migration or making YoDb the canonical write store
write routing, distributed transactions, or cross-source mutation
Qdrant, Pinecone, MongoDB, ClickHouse, S3, or generic adapter completeness
automatic datastore placement/migration or infrastructure provisioning
unbounded graph queries, arbitrary Cypher/SQL passthrough, or graph extraction
SemanticJoin, semantic ranking/map/extraction algebra beyond SemanticFilter
autonomous schema generation or broad natural-language execution without IR validation
enterprise tenancy, HA, and full governance platform
```

## Expansion path (V0.2 / V1)

New source adapters implement logical capabilities rather than a universal
`Database` interface. Likely next additions are an external vector store
(Qdrant/Pinecone), document source, analytical store, and additional model
strategies. The public IR, join bindings, explain surface, source precedence,
and planner boundary remain unchanged.

## Success criteria

V0.1 is successful when a small team can connect PostgreSQL and optionally
Neo4j without migration, issue one typed query that combines relational,
semantic, and bounded graph constraints, and receive correct normalized results
with a complete explanation.

The semantic benchmark must show meaningful reductions in model calls, cost,
and latency versus the naive baseline, with measured acceptable quality loss.
If the router cannot reliably execute declared joins or the optimizer cannot
beat a competent hand-built Postgres/pgvector/model pipeline, prioritize those
failures over adding another backend.
