# YoDb V0.1 — Implementation Plan

## Purpose and relationship to the V0.1 architecture

This is the delivery plan for YoDb V0.1. It implements the product boundary
and contracts in [v0.1-federated-semantic-data-layer.md](v0.1-federated-semantic-data-layer.md).
That document defines *what* V0.1 is; this document defines the implementation
sequence, deliverables, and completion criteria.

V0.1 is a read-only, typed, explainable data layer. It lets applications and
agents issue one logical query that can combine:

- relational reads from PostgreSQL;
- semantic predicates using PostgreSQL plus pgvector and a verification model;
- bounded graph traversal through PostgreSQL edge tables or optional Neo4j.

YoDb does not migrate source data, own source writes, provide distributed
transactions, or expose raw SQL/Cypher as its public interface.

```text
Application / Python SDK / MCP client
                 |
                 v
           typed logical query IR
                 |
                 v
    catalog validation + rule-based planner + explain
        |                   |                    |
        v                   v                    v
 PostgreSQL reads       pgvector + model     Postgres edges / Neo4j
```

## Guiding implementation rules

- Source systems remain authoritative for source data, transactions, IDs, and
  physical indexes.
- YoDb owns logical metadata, query semantics, planning, normalized result
  envelopes, provenance, and explanation.
- Callers use logical dataset, field, and relationship names only. YoDb
  resolves approved source bindings internally.
- Cross-source work requires a declared `JoinBinding`; no guessed joins and no
  invisible unbounded client-side join fallback.
- Physical indexes are planner optimizations, not part of the public API and
  not prerequisites for a logically supported operation.
- Plans must respect explicit limits on rows, transferred candidates, graph
  expansion, model calls, latency, and cost.
- Every query must be explainable and honest about source freshness,
  disagreement, and partial failure.

## Milestone 0 — Revise and lock the V0.1 contract

### Goal

Reconcile the existing Phase 0 logical domain model with the V0.1 federated,
read-only product boundary.

### Work

- Update Phase 0 semantics to distinguish V0.1 source-authoritative reads from
  a future YoDb-managed canonical write mode.
- Preserve the existing typed field model: `id`, `string`, `text`, `int`,
  `float`, `bool`, `timestamp`, `uuid`, `json`, `bytes`, and repeated values.
- Preserve strict logical-schema behavior: unknown logical fields are rejected
  by default; fields are typed; query input is validated.
- Reclassify the current in-memory record/edge create, update, delete,
  tombstone, version, and generated-ID code as future write-mode groundwork,
  not V0.1 runtime behavior.
- Define a normalized read-result envelope containing logical ID, fields,
  provenance, source read timestamp, query ID, and warnings.
- Define the V0.1 structured error families: query validation, catalog/binding,
  source capability, budget, availability, consistency/conflict, pagination,
  and internal error.

### Completion criteria

- The phase document contains no promise that V0.1 owns source writes,
  distributed transactions, or canonical persistence.
- The code and plans explicitly distinguish logical identity from source
  identity and surface source provenance.

## Milestone 1 — Catalog, source registry, and semantic metadata

### Goal

Give YoDb a reviewed, explicitly authored logical model of connected source
data.

### Data model

Implement these catalog entities:

```text
SourceSpec
  read-only connection/configuration, health, capabilities

LogicalDataset / DatasetSpec
  name, description, aliases, fields, source preference

LogicalField / FieldSpec
  type, description, aliases, safe examples or enum values, units,
  sensitivity, query capabilities, semantic eligibility

SourceBinding
  logical dataset -> PostgreSQL table/view or Neo4j label

FieldBinding
  logical field -> physical column/property and normalization rules

RelationshipBinding
  business relationship, direction, cardinality, description, aliases

JoinBinding
  approved physical equality/path resolution for a relationship

LogicalIdBinding
  source key -> deterministic logical ID plus provenance
```

### Work

- Add read-only source registry configuration for PostgreSQL and optional
  Neo4j.
- Add source health checks and capability discovery, including pgvector
  availability and vector-column/index metadata.
- Introspect PostgreSQL tables, columns, types, primary keys, foreign keys,
  and indexes.
- Introspect Neo4j labels, relationship types, properties, constraints, and
  indexes when configured.
- Expose inspection as factual raw schema/capability metadata only; do not
  infer, suggest, or generate a logical dataset, field mapping, relationship,
  cross-source match, or join.
- Define and implement the versioned three-file YAML/JSON and Python/Pydantic
  catalog contract: `logical.yaml`, `sources.yaml`, and `relations.yaml`.
  It exposes one backend-neutral source/dataset/resource/physical-field shape,
  rather than user-authored named mapping objects.
- Let a developer or coding agent author the complete declarative catalog from
  inspected schema and user-provided business context.
- Validate submitted mappings, field meanings/metadata, source precedence,
  identity keys, and join keys. Provide read-only profiling facts such as key
  uniqueness, null rate, join coverage, and duplicate counts without turning
  them into a suggested mapping.
- Validate catalog versions and mappings before activation.

### Completion criteria

A human-approved, agent-authored catalog can describe a `Customer` dataset, a
`SupportTicket` dataset, their column meanings, an approved
`Customer.has_ticket` relationship, and its physical Postgres and/or Neo4j
bindings. No logical mapping becomes active through automatic inference.

## Milestone 2 — Typed logical query IR and validation

### Goal

Define one backend-neutral public query language that applications, the Python
SDK, and later MCP tools can share.

### Initial operators

```text
Scan(dataset)
Filter(expression)
Project(fields)
Order(field, direction)
Limit(count)
SemanticFilter(field, proposition)
Traverse(relationship path, direction, hop filters)
```

### Query constraints

```text
maximum_results
maximum_latency_ms
maximum_cost
minimum_quality
allow_partial_results
```

### Work

- Build type-safe Python builders and serializable IR objects.
- Validate datasets, fields, types, operators, projections, orderings,
  relationship directions, and bounded path shape against the catalog.
- Validate all logical joins against `JoinBinding`s.
- Add a query fingerprint for cursor and session safety.
- Define signed opaque relational keyset cursors and semantic search-session
  cursor contracts.
- Return transport-neutral structured validation errors before contacting a
  source.

### Completion criteria

Made-up fields, raw SQL/Cypher, unsupported operators, undeclared joins,
unbounded traversal, and unsafe request limits are rejected before execution.

## Milestone 3 — PostgreSQL relational connector

### Goal

Deliver the first end-to-end useful query path: typed logical relational reads
from PostgreSQL.

### Work

- Compile `Scan`, `Filter`, `Project`, `Order`, and `Limit` into parameterized
  PostgreSQL operations through approved bindings.
- Push filtering, projection, order, and safe limit/top-k work to PostgreSQL.
- Normalize returned source values to declared logical field types.
- Produce deterministic logical IDs from `LogicalIdBinding` and attach source
  provenance.
- Implement stable keyset pagination with opaque signed cursors.
- Enforce source timeouts and cancellation; retry only idempotent reads when
  policy permits.
- Record source latency, scanned/returned rows, and actual plan observations.
- Capture safe PostgreSQL plan information for YoDb `EXPLAIN`.

### Completion criteria

A caller can execute a typed relational query against a logical dataset and
receive correct normalized results without supplying physical database,
table, column, index, or SQL names.

## Milestone 4 — Rule-based planner and explainability

### Goal

Create the planning boundary before adding semantic and graph execution.

### Planner pipeline

```text
validate IR
  -> resolve catalog bindings
  -> apply safe logical rewrites
  -> enumerate bounded physical alternatives
  -> estimate work and validate constraints
  -> select plan
  -> execute
  -> record actuals for telemetry
```

### Initial planning rules

- Apply selective deterministic filters early.
- Project only fields required by the query or later operators.
- Push work into a source whenever that is safe and supported.
- Apply a safe limit/top-k early.
- Prefer bounded candidate-set transfers and lower data movement.
- Reject an unbounded client-side join rather than hiding it as fallback.
- Prefer configured source precedence for final hydration.
- Reject plans that cannot meet hard row, traversal, model, cost, or latency
  budgets.

### Explain contract

Every request receives a query ID. `EXPLAIN` exposes:

- validated logical IR;
- selected datasets, source bindings, and source capabilities;
- pushed-down and YoDb-local operations;
- declared join bindings and candidate transfers;
- plan estimates and actual rows/latency where available;
- warnings about freshness, conflict, degradation, or partial failure.

### Completion criteria

A developer can determine why YoDb selected a source and join/pushdown
strategy, and compare planned work with actual work.

## Milestone 5 — pgvector semantic execution

### Goal

Implement semantic predicates without presenting a vector index as semantic
truth.

`SemanticFilter(field, proposition)` asks whether the proposition is true of a
record. Vector similarity is only a candidate-generation technique.

### Required physical plans

```text
Plan A: PostgreSQL deterministic filter
          -> model/classifier verification of every remaining candidate

Plan B: PostgreSQL deterministic filter
          -> pgvector candidate shortlist
          -> model/classifier verification
          -> preferred-source hydration
```

### Work

- Define embedding-provider and verification-model/provider interfaces.
- Record embedding model, dimensions, distance metric, and version in catalog
  metadata.
- Compile pgvector candidate retrieval through the PostgreSQL connector.
- Add a bounded exact-vector scan fallback only when embedding data exists and
  the requested work/latency budgets permit it.
- Implement conservative candidate oversampling and verification policy.
- Return verification decision, confidence/quality signal, model/provider
  version, cost, and latency as result metadata.
- Add planner estimates for cardinality, candidate size, model calls, latency,
  cost, and expected retrieval quality.
- Implement short-lived search sessions that preserve semantic ranking across
  pagination.
- Build semantic telemetry and a labeled benchmark corpus.

### Completion criteria

The retrieval-assisted plan measurably reduces model calls, cost, or latency
against Plan A while meeting an agreed quality threshold on the benchmark.

## Milestone 6 — PostgreSQL graph traversal

### Goal

Implement the required graph capability using normal PostgreSQL edge tables.

### Work

- Map `RelationshipBinding`s to PostgreSQL edge tables and endpoint keys.
- Compile bounded `Traverse` paths into parameterized SQL joins or bounded
  recursive queries.
- Support direction, configurable maximum hops (default three), and typed
  edge/target filters per hop.
- Enforce intermediate node, edge, candidate-transfer, and time budgets.
- Deduplicate returned nodes by logical ID.
- Hydrate final records through configured preferred source bindings.
- Include graph expansion, selected edge representation, and work budgets in
  explain/telemetry output.

### Completion criteria

One query can combine relational filtering, a bounded declared relationship
path, and relational projection, without unbounded expansion.

## Milestone 7 — Optional Neo4j graph adapter and cross-source composition

### Goal

Add Neo4j as an alternative graph execution target without adding a second
public graph language.

### Work

- Compile approved `Traverse` IR into bounded parameterized Cypher.
- Restrict labels, relationship types, and properties to reviewed mappings.
- Transfer only bounded candidate IDs through explicit Postgres-to-Neo4j or
  Neo4j-to-Postgres `JoinBinding`s.
- Prevent full-source scans and unbounded local joins.
- Hydrate returned records from the configured preferred source.
- Surface source health, read timestamp, selected graph implementation, and
  partial-source conditions.

### Completion criteria

The same logical graph query can run through PostgreSQL edge tables or Neo4j
without the caller changing query shape.

## Milestone 8 — Consistency, conflict, and failure semantics

### Goal

Make federation transparent rather than implying unsupported global guarantees.

### Work

- Attach per-source read timestamp/freshness metadata to results.
- Document that V0.1 has no distributed transaction and no global snapshot.
- Enforce metadata-declared source precedence for overlapping logical fields.
- Emit a conflict warning when preferred and secondary sources disagree.
- Fail closed when a required source is unavailable by default.
- Allow partial results only when `allow_partial_results=True`; identify the
  failed source, skipped operation, and impact in the response.
- Propagate cancellation and timeouts to adapters.
- Apply safe retry rules only to idempotent read operations.

### Completion criteria

Callers can distinguish complete answers, source-stale answers, conflicting
source values, and explicitly degraded partial answers.

## Milestone 9 — MCP and agent integration

### Goal

Expose the reviewed logical catalog and safe query runtime to agents without
giving them unrestricted database access.

### MCP tools

```text
search_catalog(query)
describe_dataset(dataset)
get_catalog_neighborhood(entity, depth)
get_relationships(dataset)
validate_query(ir)
explain_query(ir)
execute_query(ir)
```

### Catalog information exposed to agents

- dataset and field descriptions;
- aliases and safe example values;
- relationship meanings, directions, and cardinalities;
- allowed logical query capabilities;
- sensitivity/access constraints;
- ambiguity candidates for clarification.

The normal MCP interface uses logical names. Physical source table/column
details are restricted to authorized developer/debug explain output. The MCP
server is read-only and is not a raw SQL/Cypher proxy.

### Completion criteria

An agent can discover a reviewed concept graph, propose a typed query, validate
it, explain it, and execute it without receiving database credentials or
inventing physical column/join names.

## Milestone 10 — Evaluation, security, and release hardening

### Work

- Unit tests for catalog validation, bindings, logical IDs, IR, cursors,
  source adapters, and planner rules.
- PostgreSQL + pgvector integration tests and optional Neo4j integration tests.
- Fixture datasets that exercise relational, semantic, graph, and combined
  queries.
- Golden `EXPLAIN` snapshots.
- Labeled semantic evaluation corpus with expected matches, candidate recall,
  verification quality, model calls, latency, and cost.
- Adversarial tests for invented fields, invalid joins, injection attempts,
  excessive budgets, connector failure, stale/conflicting values, and sensitive
  field access.
- Verification of least-privilege, read-only source credentials.
- Benchmarks against a competent hand-built PostgreSQL/pgvector/model baseline.
- Python SDK documentation and end-to-end examples.

### Completion criteria

V0.1 can demonstrate a correct, explainable combined relational + semantic +
bounded graph query with source provenance, bounded work, and meaningful
semantic-plan improvement over the naive verification baseline.

## Required delivery order

```text
M0 contracts
  -> M1 catalog and source registry
  -> M2 typed IR
  -> M3 PostgreSQL relational connector
  -> M4 planner and explain
  -> M5 pgvector semantic execution
  -> M6 PostgreSQL graph traversal
  -> M7 optional Neo4j adapter
  -> M8 consistency/failure hardening
  -> M9 MCP integration
  -> M10 evaluation and release hardening
```

The sequence is intentionally strict: each later capability depends on a
reviewed catalog, a validated logical query, and a visible planner boundary.
